# И14 — Вторая специализация кандидата

Готово в `/srv/work/srv/work/spectrek/wt/multispec`, ветка `feat/multispec`. Сервер и общий стенд не менял; выкладка — координатором.

## Что сделано

1. **Два направления с независимыми тестами.** Опрос принимает основное и дополнительное направления, отдельный стек для каждого. Перед тестом кандидат выбирает направление и грейд. Для правил смены грейда берутся категория и `locked_until` именно этого направления. Активная сессия другого направления не прерывается; предыдущие субпулы и семейства для повторного теста выбираются только из своих попыток. Неудача дополнительного теста не меняет основной грейд. Повторный `finish` идемпотентен.
2. **Модель и миграция.** Таблица `candidate_specializations`: `(user_id, direction_id)`, `is_primary`, грейд, категория, статус, θ, SE, рейтинг, `locked_until`, ссылка на подтверждающий тест, дата подтверждения. История остаётся в существующей `grade_history`, по паре пользователь–направление; API отдаёт её также внутри каждой специализации. Миграция **`ms01`, `down_revision = "qr01"`** переносит основную категорию, блокировку, рейтинг, результат теста и направление последнего опроса для ещё не подтверждённых профилей. История и исходный профиль не удаляются. Уникальные частичные индексы ограничивают профиль одной основной и одной дополнительной записью, CHECK проверяет соответствие категории направлению и грейду. В PostgreSQL изменение направлений сериализуется блокировкой строки профиля.
3. **Совместимость.** `candidate_profiles.current_*`, `grade_locked_until`, `rating_score` зеркалируют только основное направление. Старые сиды и интеграции, записывающие эти поля, читаются через переходный адаптер без обязательного изменения их кода. Существующие 150 демо-кандидатов, их идентификаторы и `demo/seed.py` не менял.
4. **Подбор, поиск и доказательства.** Кандидат находится по категории основного либо дополнительного направления, но появляется в общей выдаче один раз. θ, SE, навыки T1, зонды и рейтинг выбираются в контексте нужного направления. Новые результаты одного теста не удаляют факты другого; направление старых фактов восстанавливается по сессии, потребности зонда или категории кубка. Зонд Backend не усиливает Frontend. Карточка из поиска сохраняет контекст направления; сравнение использует направление потребности. Доказательства в приглашении также относятся к нужному направлению.
5. **Показ кандидату и работодателю.** Обзор, «Категория и грейд», карточка работодателя, сравнение и PDF показывают обе специализации, основную/дополнительную и пометку «подтверждено отдельным тестом · T1». Опрос без теста не выдаётся за подтверждение и не создаёт категорию для поиска. Для обратной связи по умолчанию используется последний тест основного направления; по `session_id` можно открыть тест дополнительного. `/api/me` возвращает массив специализаций в дополнение к прежним полям.
6. **Демо и проводник.** В новой песочнице Мария Королёва имеет Backend · Middle и Frontend · Junior. Второе направление подтверждается отдельным прохождением настоящего движка банка за синтетического демо-респондента, а не ручной пометкой. Шаг «Присвоение категории» объясняет две специализации и независимые ограничения.
7. **Исправление, найденное в браузере.** При быстрой смене направления и грейда запоздавший ответ поиска мог заменить более новую выдачу. В `useApi` добавлен номер запроса и игнорирование старых ответов. Проверено с намеренно задержанным запросом «все направления».

Основной код: `backend/app/modules/profiles/specializations.py`, `profiles/models.py`, `profiles/facts.py`, `assessment/service.py`, `assessment/review.py`; новый компонент `frontend/src/components/Specializations.tsx`.

## Принятые умолчания, ограничения и что осталось координатору

- Максимум два направления. Добавление/редактирование опроса не удаляет уже созданные направления и подтверждённые категории; основная категория сохраняется для совместимости. Удаление специализации и смену метки «основное» не делал. Альтернатива для будущего — отдельное явное действие удаления неподтверждённого направления или назначения основной специализации, не неявная потеря теста при редактировании опроса.
- Старые уже созданные песочницы не обновляются автоматически. Для двух специализаций нужен новый `scenario: "new"` или штатный сброс **своей** песочницы. Старые сохранённые версии подборок остаются снимками прежнего состояния; новая специализация учитывается при создании следующей версии.
- Аналитика ФСП сохраняет прежнюю группировку по основной категории: кандидата не удваиваем. Поиск и счётчики категорий работодателя учитывают обе.
- Миграция написана переносимо для SQLite/PostgreSQL (обычные FK, Boolean, DateTime, частичные индексы и конкатенация строк), **реальный прогон PostgreSQL 16 не выполнялся**. Проверить на серверной БД после выстраивания общей цепочки миграций.
- Выполнить слияние с И1/И13, затем общий регрессионный прогон и e2e на стенде. Самостоятельную выкладку, перезапуск стенда и push не делал.
