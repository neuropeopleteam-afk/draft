# Интеграция с ФСП ID

В прототипе «ФСП ID (демо)» — это Keycloak 26 (официальный образ `quay.io/keycloak/keycloak`) с realm `fsp`,
который играет роль единой учётной записи участника соревнований ФСП. Платформа подключается к нему как обычный
OIDC-клиент, поэтому замена демо-стенда на настоящий ФСП ID — это смена адреса, client_id и секрета, без
изменения кода: имена claims задаются через JSON-настройку `FSP_OIDC_CLAIMS_MAP`.

Код: `backend/app/integrations/fsp_id/` (OIDC, маппинг, API), `keycloak/` (образ, генератор realm),
фронтенд `frontend/src/integrations/FspId.tsx`.

### Метки происхождения данных (Я8)

Каждое значение интеграций ФСП, ФНС и ATS в интерфейсе подписано одной из четырёх меток (компонент
`frontend/src/components/Origin.tsx`, источник правды — `backend/app/core/origin.py`, тест `tests/test_origin.py`):

| Метка | Когда | Примеры |
|---|---|---|
| «модельные данные» | сведения сгенерированы для демо | демо-паспорт ФСП (`link_source=demo`), демо-сведения ФНС у демо-компаний без ИНН |
| «заглушка по спецификации» | настоящий HTTP тем же кодом, но отвечает наша заглушка по публичной спецификации | демо-стенд ФСП ID (Keycloak) при `FSP_ID_DEMO=true`, мок реестра ФСП, демо-ATS |
| «реальный запрос» | ответ внешней системы | egrul.nalog.ru, ФСП ID / реестр при боевых настройках, ATS с токеном и успешной проверкой связи |
| «не проверено» | запроса не было или он не удался | капча ФНС, нет ИНН, ATS без токена или без успешной проверки |

Метка — только подпись источника: индекс доверия, бонус ФСП и ранжирование от неё не зависят.
Отсутствие истории ФСП везде описано одной фразой: «Истории ФСП нет — без штрафа; подтверждённые достижения ФСП
дают бонус» (`NO_FSP`).

## 1. Развёртывание

| Что | Как |
|---|---|
| Сервис | `keycloak` в `docker-compose.yml`, профиль `fsp-id` (`COMPOSE_PROFILES=fsp-id`) |
| Адрес | тот же домен, путь `/auth` (`KC_HTTP_RELATIVE_PATH=/auth`), nginx контейнера `web` проксирует `/auth/` |
| Закрыто снаружи | `/auth/admin/` и `/auth/realms/master/` → 403; админка доступна только с сервера на `127.0.0.1:8142` |
| Хранилище | отдельная база `keycloak` в нашем PostgreSQL (создаётся скриптом `db/initdb/10-keycloak.sh`) |
| Память | лимит контейнера 640 МБ, `MaxRAMPercentage=40`, `TieredStopAtLevel=1`, локальный кэш; на сервере ≈ 330–400 МБ |
| Realm | `keycloak/realm-fsp.json` генерирует `keycloak/make_realm.py`; импорт при старте (`--import-realm`, существующий realm не перезаписывается) |
| Секреты | `FSP_OIDC_CLIENT_SECRET`, `FSP_DEMO_PASSWORD` — `secrets/fsp_id.env`; пароль администратора — `secrets/keycloak.env`; вне репозитория, `chmod 600` |

## 2. Поток входа (Authorization Code + PKCE, backend-for-frontend)

```
Браузер                Платформа (api)                         Keycloak realm fsp
  │ «Войти через ФСП ID»   │                                        │
  ├─ POST /api/fsp-id/start ─▶ state, nonce, code_verifier → БД     │
  │◀── authorize_url ──────┤  (code_challenge = S256)               │
  ├────────────────────────────── GET /auth/realms/fsp/…/auth ─────▶│ логин и пароль
  │◀────────────── 302 /api/fsp-id/callback?code&state ─────────────┤
  ├─ GET /api/fsp-id/callback ─▶ POST token (code + code_verifier) ─▶│
  │                        │  проверка id_token по JWKS: подпись, iss, aud, exp, nonce, azp
  │                        │  claims → одноразовый билет (5 мин)
  │◀── 303 /fsp-id/done?ticket=… ┤
  ├─ POST /api/fsp-id/exchange ─▶ JWT платформы (известный пользователь)
  │                        │  или consent_required + превью паспорта (новый)
  ├─ POST /api/fsp-id/complete (согласие 152-ФЗ) ─▶ кабинет выбранной роли + JWT
```

- Токены Keycloak в браузер не попадают; браузер получает только JWT платформы.
- Новая учётная запись создаётся **только после согласия** на обработку ПДн; почта считается подтверждённой, если ФСП ID передал `email_verified=true`.
- Если почта уже занята аккаунтом с паролем — автоматической склейки нет: пользователь входит паролем и
  связывает ФСП ID в разделе «Паспорт ФСП» (`intent=link`, повторный ввод пароля в Keycloak — `prompt=login`).
- Обращение к Keycloak с сервера идёт по внутренней сети (`FSP_OIDC_INTERNAL_BASE=http://keycloak:8080/auth/realms/fsp`),
  а `iss` проверяется по публичному адресу (`FSP_OIDC_ISSUER`). Keycloak с `KC_HOSTNAME_BACKCHANNEL_DYNAMIC`
  выдаёт одинаковый `iss` для обоих путей.

## 3. Claims и паспорт ФСП

Клиент `spectrek-platform` (confidential, PKCE S256, redirect `…/api/fsp-id/callback`) содержит мапперы
пользовательских атрибутов в id_token, access_token и userinfo:

| Claim | Тип | Пример | Куда в платформе |
|---|---|---|---|
| `sub` + `iss` | строки | UUID Keycloak + issuer | хеш пары в `users.fsp_subject`, `fsp_passports.fsp_subject` (уникально) |
| `email`, `email_verified` | строка, bool | `champion@demo.fsp-id.example` | почта новой учётной записи |
| `fsp_id` | строка | `FSP-770012` | номер в паспорте, `candidate_profiles.fsp_id_claimed` (подтверждён) |
| `fsp_rank` | строка | `КМС` | `fsp_passports.sport_rank` — разряд по ЕВСК |
| `fsp_disciplines` | массив | `["product", "algorithmic"]` | дисциплины ЕВСК (справочник `FSP_DISCIPLINES`) |
| `fsp_achievements` | массив JSON | `{"discipline":"product","event":"…","level":"national","date":"2025-11-22","place":1,"result":"победитель"}` | `fsp_achievements`, `verified=true` |

- Уровень доказанности всех фактов из ФСП ID — **T2** («подтверждено реестром»); они участвуют в бонусе рейтинга.
- Неизвестные дисциплины и уровни (`school | regional | interregional | national | international`) отбрасываются.
- ФИО из ФСП ID не копируется в карточку — обезличенность сохраняется, контакты раскрываются по правилам платформы.
- Пользователь без claims `fsp_*` получает связанный паспорт без достижений — без штрафа; подтверждённые достижения ФСП дают бонус (у него бонуса нет).

Демо-пользователи realm `fsp` (пароль — в подсказке на странице входа, на сервере задан в `secrets/fsp_id.env`):

| Логин | Профиль |
|---|---|
| `fsp-champion` | КМС, продуктовое и алгоритмическое программирование, 3 достижения (в т. ч. всероссийский уровень) |
| `fsp-prizer` | II разряд, программирование систем ИБ, призёр |
| `fsp-newcomer` | нет истории соревнований ФСП |

## 4. API платформы

| Метод | Назначение |
|---|---|
| `GET /api/fsp-id/config` | включён ли вход, подпись кнопки, демо-учётки |
| `POST /api/fsp-id/start` `{intent: login|link, registration_role: candidate|employer}` | начать вход или связку → `authorize_url`; роль новой учётки сохраняется в серверном state |
| `GET /api/fsp-id/callback` | redirect_uri для Keycloak |
| `POST /api/fsp-id/exchange` `{ticket}` | билет → JWT или запрос согласия |
| `POST /api/fsp-id/complete` `{ticket, consent_processing, consent_publication, company_name?}` | создать кабинет выбранной роли после согласия; название компании для работодателя |

## 5. Как подключить настоящий ФСП ID

1. Зарегистрировать платформу как OIDC-клиента ФСП ID: тип confidential, Authorization Code + PKCE (S256),
   redirect URI `https://<домен>/api/fsp-id/callback`, scopes `openid email profile` и scope с атрибутами паспорта.
2. Согласовать состав claims с ФСП. Если имена отличаются (например, `evsk_rank` вместо `fsp_rank`) —
   задать `FSP_OIDC_CLAIMS_MAP={"fsp_rank":"evsk_rank"}`. Поддерживаются вложенные пути:
   `{"fsp_id":"participant.id","fsp_achievements":"participant.results"}`.
   Если реестр достижений отдаётся отдельным API, включить `FSP_REGISTRY_MODE=external` и задать его адрес и сервисный токен.
3. Задать переменные: `FSP_OIDC_ISSUER` (issuer ФСП ID), `FSP_OIDC_INTERNAL_BASE` — тот же issuer для внешнего стенда,
   `FSP_OIDC_CLIENT_ID`, `FSP_OIDC_CLIENT_SECRET` (в `secrets/fsp_id.env`), `FSP_DEMO_ACCOUNTS=` и
   `FSP_DEMO_PASSWORD=` — пусто (подсказка с демо-учётками скрывается).
4. Убрать профиль `fsp-id` из `COMPOSE_PROFILES` — демо-Keycloak больше не запускается.
5. Проверить: `/.well-known/openid-configuration` ФСП ID доступен с сервера; вход тестовым участником;
   в паспорте появились достижения с отметкой T2.

Для production дополнительно: refresh-токены не храним (данные паспорта обновляются при каждом входе);
периодическая синхронизация достижений и отзыв связки при удалении учётной записи в ФСП ID — следующий этап.

## 6. Переключить на стенд ФСП за 15 минут

Предусловие: ФСП уже выдала issuer, client_id, секрет, scopes, пример claims и зарегистрировала callback.
15 минут — время переключения готового клиента, не обещание получить доступ за этот срок.
На сервере команды это выполняет только координатор.

| Минуты | Действие | Контроль |
|---|---|---|
| 0–3 | Зарегистрировать/проверить callback `https://<наш-домен>/api/fsp-id/callback`; Authorization Code + PKCE S256 | Callback разрешён ровно для домена платформы |
| 3–5 | Обновить `secrets/fsp_id.env`: issuer, client_id, secret, scopes, claims map, `FSP_ID_DEMO=false` | Секреты не в Git; файл с правами 600 |
| 5–7 | Проверить `FSP_OIDC_INTERNAL_BASE`: при внешнем issuer задать **тот же внешний issuer** в `.env` compose | Иначе compose сохранит демо-backchannel `keycloak:8080` |
| 7–9 | Прочитать discovery с сервера; `issuer` должен совпадать с настройкой. Указать поддерживаемый `FSP_OIDC_TOKEN_AUTH_METHOD` | `client_secret_basic`, `client_secret_post` или `none` для public-клиента |
| 9–11 | Координатор пересоздаёт только `api` после резервной копии; отключает демо-профиль Keycloak, если больше не нужен | `/api/fsp-id/config`: enabled=true, demo=false, демо-пароль отсутствует |
| 11–13 | Вход новым тестовым участником через `/register`: кандидат **или работодатель** | Согласие → нужный кабинет; для работодателя заполняется название компании |
| 13–15 | Связка существующего кандидата и повторный вход; участник с историей/без истории | Связь «ФСП ID ↔ профиль», достижения/нейтральное состояние, дублей нет |

Пример **несекретных** настроек (реальные значения выдаёт ФСП):

```dotenv
FSP_OIDC_ISSUER=https://<стенд-ФСП>/<issuer>
FSP_OIDC_INTERNAL_BASE=https://<стенд-ФСП>/<issuer>
FSP_OIDC_CLIENT_ID=<выданный-client-id>
FSP_OIDC_SCOPES=openid email profile
FSP_OIDC_DISCOVERY=true
FSP_OIDC_TOKEN_AUTH_METHOD=client_secret_basic
FSP_OIDC_CLAIMS_MAP={"fsp_id":"participant.id","fsp_rank":"participant.rank","fsp_achievements":"participant.results"}
FSP_ID_DEMO=false
```

`FSP_OIDC_CLIENT_SECRET` и `FSP_REGISTRY_TOKEN` — только в файле секретов.
Переменные клиента/scopes/маппинга можно задавать там же; compose явно переопределяет только issuer и internal base,
поэтому для них используется `.env` compose. Откат: вернуть прежний env-файл и пересоздать api; данные паспортов остаются.

Discovery используется по умолчанию: серверные endpoint'ы берутся из `/.well-known/openid-configuration`,
а не из фиксированных Keycloak-путей. Кэш — до 5 минут. При ошибке/несовпадении issuer вход возвращает понятную
ошибку, **не** переходит молча на предполагаемые адреса. `FSP_OIDC_DISCOVERY=false` — явный совместимый режим
для старого демо-Keycloak; он использует стандартные пути Keycloak.
Стандартные поля подписи `sub`, `iss`, `aud`, `exp`, `nonce` не переименовываются маппингом.
Идентичность хранится как хеш пары issuer + sub: одинаковый sub двух стендов не связывает разных людей.
Старые связи с демо-Keycloak обновляются только при совпадении записанного issuer.

## 7. Реестр: контракт и рабочий адаптер

`docs/fsp_registry_api.yaml` — **предложение команды**, не утверждённый ФСП контракт.
Мок реализован в `backend/app/modules/fsp/registry.py`, экспорт спецификации:

```bash
python tools/export_fsp_registry_api.py
curl http://127.0.0.1:8106/api/fsp-registry/v1/participants/FSP-770012/achievements
```

Снимок содержит версию схемы, ФСП ID, разряд, дату обновления и до 1000 результатов:
устойчивый ID достижения/мероприятия, тип и уровень мероприятия, дисциплину, код ЕВСК, дату, место,
тип результата, разряд за событие, команду (ID, название, место, число участников, роль).
Официальных кодов ЕВСК организатор не предоставил: поле `evsk_code=null`, вымышленные коды не выдаём за реальные.
ФИО/контактов участников и состава команды в контракте нет.

- `FSP_REGISTRY_MODE=claims` (по умолчанию): паспорт приходит в OIDC claims.
- `FSP_REGISTRY_MODE=mock`: встроенный синтетический снимок; если задан `FSP_REGISTRY_BASE_URL`,
  запрос идёт **по HTTP** в мок по контракту.
- `FSP_REGISTRY_MODE=external`: HTTP GET к `<base>/participants/<подтверждённый-fsp-id>/achievements`,
  сервисный Bearer из `FSP_REGISTRY_TOKEN`, тайм-аут `FSP_REGISTRY_TIMEOUT_S` (5 с).
- Мок знает только `FSP-770012`, `FSP-770013`, `FSP-770014` (победитель, призёр, без истории).
  Он публичный, потому что содержит исключительно синтетические сведения. Настоящий API должен быть закрыт.
- `POST /api/me/fsp/registry-sync`: обновление своего **уже связанного** паспорта; вручную введённый номер
  не позволяет получить T2. У Марии в новой песочнице жюри кнопка обновляет паспорт из синтетического мока.
- При сбое реестра OIDC-вход остаётся доступным; старые достижения не стираются. Нет новых доказательств —
  нет нового бонуса. Повторная синхронизация заменяет снимок, не копит дубли; записи кубков платформы T1 сохраняются.
- Для большого реестра нужны пагинация, журнал изменений и правила отзыва подтверждения; это следующий этап,
  а не скрытая возможность мока.

Идея полей и равных весов соответствует разбору видео организаторов, №55–57, №61 (46:42–50:40; 53:44–55:16). Отдельного официального API на дату разработки не предоставлено.

## 8. Рейтинг ФСП v2 и несовершеннолетние

Формула в `modules/fsp/rating.py`, версия `fsp-v2`: только verified/T2, одинаково для всех направлений,
дисциплин и уровней/типов соревнования. Победитель — 1; призёр — 0,85; финалист — 0,60; участник — 0,15.
Вес давности `d=1` первые 365,25 дня, затем `d=0,7+0,3·exp(−(лет−1)/3)`.
Для результатов `v` по разным событиям сила равна `0,8·max(v)+0,2·(1−exp(−sum(остальных v)))`.
Число событий берётся по `event_id`; у старых данных — название + дата.
Разряд и индивидуальный вклад в команду показываются, но не дают произвольных множителей.
Без даты вес полный, будущая дата надбавку не даёт. Отсутствие ФСП — 0 без штрафа; грейд ФСП не меняет.
Вес ФСП в скоре подбора остаётся 0,10. Внутри общего рейтинга категории сохранены прежние веса 0,65/0,10/0,25.

**Релевантность дисциплины специализации (флаг `FSP_DISCIPLINE_RELEVANCE`, по умолчанию выключен).** Ответ
организаторов (E08): дисциплины одинаково приоритетны, но можно учитывать актуальность направления — ИБ-специалист с
соревнованиями по ИБ релевантнее, чем с соревнованиями по робототехнике. `modules/fsp/relevance.py` задаёт мягкий
коэффициент пары «дисциплина — направление кандидата»: близко — 1,0, смежно — 0,9, дальше — 0,8 (например,
продуктовое программирование близко к Backend, Frontend и QA; алгоритмическое — к Backend и Data/ML; ИБ — к ИБ;
робототехника и БАС — к Data/ML, своего направления embedded/robotics в MVP нет). Дисциплины между собой равны: у
каждой есть направления, где она «близко» (инвариант проверяет тест), коэффициент зависит только от пары. При
включённом флаге он умножает вклад результата в силу паспорта (`rating.details(…, direction, relevance=True)`), в
объяснении подбора и в карточке появляется строка «Соревнования по «…» — близко к специализации кандидата
(коэффициент 1,0)», а в описании формулы — правило коэффициента. Влияние на итоговый скор — не больше
0,10 × 0,2 = 0,02. При выключенном флаге ответ `details` байт-в-байт прежний, порядок match-v1 не меняется.

Замер (09.10.2026, `make bench` 200 × 2000, seed по умолчанию, флаг выкл. → вкл.) на ветке после слияния
integ/0710 b2e8dfe (match-v1.1 с ярусами обязательного): p@5 0,759 → 0,759, p@10 0,738 → 0,740, nDCG@5 0,574 → 0,574,
nDCG@10 0,562 → 0,562, MRR 0,877 → 0,877; второй мир (seed + 1): p@10 0,723 → 0,722, nDCG@5 0,560 → 0,559,
nDCG@10 0,546 → 0,545, MRR 0,869 → 0,864. До слияния (база c1c248e) — так же: p@5 0,769 → 0,768, MRR 0,883 → 0,885;
`tools/realdata/ranking_guard.py` (скрытая истина 50 × 500): nDCG@10 0,5729 → 0,5728, MRR 0,8223 → 0,8233, демо-500 без
изменений. Изменения в пределах шума (95 % интервалы перекрываются почти полностью), но часть метрик второго мира чуть

Возрастная группа (18+ / 16–17 / 14–15) и отметка согласия представителя — самоописание, не проверка документов.
Дата рождения не собирается. В ранжировании и фильтрах возраста нет; «Красная кнопка» меняет группы и отметку
согласия на всех кандидатах и проверяет неизменность выдачи.
Для 16–17 отправка/принятие оффера требует отметки согласия, формата `internship|light_work`,
`reduced_time=true`, `employer_acknowledged=true`. Проверка централизована и действует также для
автоприглашений кубков: обычный взрослый оффер несовершеннолетнему автоматически не отправится.
Для 14–15 профиль/тест доступны, отправка оффера в MVP блокируется: нужна отдельная проверка условий.
Не добавлены юридические страницы и проверка документов — только короткие тексты в профиле/оффере.
