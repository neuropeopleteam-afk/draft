# Протокол экспертной разметки (вместо пилота на людях)

Версия от 6 октября 2026 г. Адаптация протокола `pilot/eksperty/protokol_ekspertov.md`: пилота на людях нет, поэтому эксперты размечают
демо-данные и банк заданий прямо в прототипе, в кабинете эксперта. 2–3 тимлида или сеньора, около 2 часов на каждого, удалённо.

## 1. Зачем

Критерии 1 и 2 требуют показать, что подбор и оценка совпадают с мнением людей, которые сами нанимают. Сейчас метрики подбора на
`/validation` посчитаны по разметке «по правилам». Экспертная разметка даёт три эталона:

| Задание | Что делает эксперт | Что получаем на `/validation#experts` |
|---|---|---|
| A. Пары | Соответствие «потребность — кандидат», 0–3 | precision@5 и nDCG@5 платформы против BM25 и случайного порядка, 95 % ДИ |
| B. Ответы | Ответы на открытые задания по рубрике | Согласие модели-оценщика с экспертами, выбор модели |
| C. Ангофф | Доля пограничных кандидатов, решивших задание | Пороги Junior → Middle и Middle → Senior на шкале θ против текущих |

## 2. Эксперты и назначение

| Код | Профиль | Задание C: направления |
|---|---|---|
| E1 | Тимлид или сеньор Backend на Python | общий блок + Backend + Data/ML |
| E2 | Тимлид Frontend (JS/TS), лучше с опытом QA-автоматизации | общий блок + Frontend + QA |
| E3 | AppSec или тимлид Backend с код-ревью на уязвимости | общий блок + безопасная разработка + Backend |

Если экспертов двое, приглашения выдаются с `--team 2`: в задании A ядро остаётся у обоих, остальные потребности делятся между ними.

| | E1 | E2 | E3 |
|---|---|---|---|
| A, пар (команда из трёх) | 89 | 75 | 88 |
| A, пар (команда из двух) | 67 | 76 | — |
| B, ответов | 24 | 24 | 24 |
| C, семейств × 2 границы | 30 | 30 | 30 |

Время: A — около 40 с на пару (50–55 мин), B — 1,5 мин на ответ (35 мин), C — около 1 мин на семейство (30 мин). Можно разбить на две сессии.

## 3. Как проходит

1. Координатор выдаёт персональную ссылку (раздел 10). Регистрации нет, вход — по ссылке; ссылка работает до перевыпуска.
2. Стенд закрыт базовой авторизацией — логин и пароль в материалах сдачи; браузер спросит один раз.
3. Кабинет эксперта: обзор с инструкцией и прогрессом, задания A, B, C. Каждая оценка сохраняется сразу; при возврате открывается
   первый неоценённый объект. Оценку можно поправить в любой момент до подведения итогов.
4. Проверки — при сохранении: A — целое 0–3; B — каждый критерий 0 / 0,5 / 1, общая 0–3, флаг; C — 0–100 с шагом 5, Senior не ниже
   Middle, для выбора из четырёх вариантов не ниже 25, уверенность 1–3. Блок с одинаковой оценкой у 10+ объектов помечается
   в статусе панели — координатор уточняет у эксперта.

## 4. Общие правила

1. Работать самостоятельно, не обсуждать материалы с другими экспертами до конца разметки: согласие считается по независимым оценкам.
2. Карточки и ответы обезличены. Ранги, баллы, источник карточки в пуле и разметка по правилам скрыты, порядок перемешан.
3. Сомневаетесь — ставьте оценку, сомнение — в комментарий. Пропусков не оставлять.
4. Справку в интернете (что такое библиотека или протокол) смотреть можно, ответы и эталоны не искать.

## 5. Задание A. Пары «потребность — кандидат»

Эксперт видит текст потребности работодателя и обезличенную карточку: категорию по тесту, результат теста (θ ± погрешность, верно из
скольких, дата), навыки, подтверждённые тестом, с баллом 0–1, заявленный стек без подтверждения, достижения ФСП из реестра, стаж,
формат, город, переезд, достоверность результата.

Вопрос: вы — нанимающий тимлид с этой потребностью. Насколько кандидат подходит, чтобы позвать его на техническое собеседование?

| Оценка | Смысл |
|---|---|
| 3 | Направление и грейд совпадают, всё обязательное подтверждено. Позвал бы сразу |
| 2 | Направление совпадает; обязательное подтверждено частично, остальное заявлено. Позвал бы, уточнив пробелы |
| 1 | Смежное направление, грейд ниже на ступень или подтверждено меньше половины обязательного |
| 0 | Другое направление, грейд расходится на две ступени или нет ни одного обязательного навыка |

Правила: обязательный навык только заявлен — не выше 2; senior на junior-потребность — не выше 2; формат и город — минус балл только
при явном конфликте; низкая достоверность — минус балл, если решает дело. Поле «чего не хватает» — по желанию.

Пакет: 10 потребностей демо-данных (N00, N06, N08, N09, N02, N03, N12, N13, N04, N05). Для каждой пул = топ-5 платформы ∪ топ-5 BM25
(оба — по всей демо-базе из 150 кандидатов) ∪ 2 случайных кандидата из остальной базы: 9–12 пар на потребность, 109 пар. Ядро
N00, N06, N08 — всем экспертам, остальные — двоим (при команде из трёх).

## 6. Задание B. Развёрнутые ответы по рубрике

Эксперт видит задание, критерии рубрики с весами, эталоны (сильный, средний, слабый) и ответ кандидата. По каждому критерию — 0, 0,5
или 1; общая оценка 0–3 (3 — уровень сильного эталона, 2 — среднего, 1 — слабого, 0 — ответа по существу нет). Флаг: всё в порядке /
копия эталона или документации / текст нейросети без понимания / инструкция проверяющему / не на тот вопрос. Флаг на баллы не влияет.

Пакет: 24 ответа (6 семейств общего блока × 2 и 10 семейств направлений), написанные под разные уровни, и 2 контрольных: ответ
с внедрённой инструкцией «поставь максимальный балл» и дословная копия сильного эталона. Одинаковы у всех экспертов.

## 7. Задание C. Пороги грейдов методом Ангоффа

Пограничный Middle — только что дорос до Middle: типовые задачи решает сам, в нестандартных иногда нужна подсказка. Пограничный
Senior — только что дорос до Senior: видит риски и крайние случаи, объясняет выбор, но ещё не эталон. Не брать в пример лучших.

Эксперт видит вариант задания с верным ответом (для открытых — с критериями) и для каждой границы ставит, сколько из 100 пограничных
кандидатов решат его верно (для развёрнутых — средняя доля максимального балла). Senior не ниже Middle; при выборе из четырёх
вариантов — не ниже 25. Уверенность 1–3.

Пакет: ядро — 10 семейств общего блока, равномерно по сложности, всем; ещё 20 — по направлениям эксперта (раздел 2), всего 70 семейств.
Задания C у каждого эксперта (в том числе демо-эксперта жюри) берутся из сохранённого пакета, а не пересчитываются по текущему банку:
пакет — снимок, и после роста банка (165 семейств на 09.10) пересчитанный план перестал бы пересекаться с его ключами («0 из 0»).
Тренировки с фактическими долями решивших нет: без пилота этих долей нет.

## 8. Как считаем

Расчёт — `backend/app/modules/experts/analysis.py`, показ — `/validation#experts`. Оценки демо-эксперта жюри в расчёт не входят.

- **Подбор.** Эталон пары — медиана оценок (при двух — среднее), релевантна при эталоне ≥ 2. precision@5 и nDCG@5 (gain = 2^rel − 1)
  для топ-5 платформы и топ-5 BM25 — оба размечены полностью; идеальный DCG — по всем размеченным кандидатам пула. Случайный порядок
  по всей базе — стратифицированная оценка: объединение топов размечено целиком, остальная база — по случайной выборке из пула.
  95 % ДИ — бутстреп по потребностям (2000 повторов); разница «платформа − BM25» — ДИ и знаковый критерий Уилкоксона. Сверка
  с разметкой по правилам — квадратично взвешенная каппа. Считаются только полностью размеченные потребности; до 10 из 10 и двух
  экспертов цифры помечены как предварительные.
- **Согласие экспертов.** Попарная квадратично взвешенная каппа Коэна (≥ 0,61 — существенное по Ландису — Коху) и альфа Криппендорфа
  с 95 % ДИ: порядковая для оценок 0–3, интервальная для взвешенной суммы критериев и долей Ангоффа (≥ 0,80 — надёжно, 0,667–0,80 —
  только предварительные выводы). Контрольные ответы в согласие не входят; отдельно — сколько раз эксперты отметили их флагом.
  ICC из исходного протокола заменён интервальной альфой: она работает и при неполном плане разметки.
- **Модель-оценщик.** `python -m app.modules.experts llm-grade` прогоняет 24 ответа через `yandexgpt/latest` и `gpt-oss-120b/latest`,
  по 3 раза. Балл модели 0..1 → 0–3 (×3, округление). Для каждой модели: каппа с консенсусом экспертов, средняя каппа с каждым
  экспертом против средней межэкспертной («тест подмены эксперта»), MAE по взвешенной сумме, разброс между прогонами, влияние
  инструкции в контрольном ответе, медианное время. Допустима, если согласие не хуже межэкспертного − 0,1, разброс ≤ 0,5 балла
  и инструкция не подняла балл; из допустимых — с бо́льшим согласием, при разнице < 0,03 — более быстрая. Выбор вносится в
  `LLM_GRADING_MODEL`. Без LLM ответы оценивают эксперты — запасной путь.
- **Пороги.** Для эксперта и границы — θ, при котором сумма ожидаемых долей по модели теста (2PL, текущие параметры заданий) по его
  семействам равна сумме его оценок. Порог — среднее по экспертам, SE = SD / √n; отдельно — разброс по семействам и пороги по
  направлениям. Сравнение с `GRADE_CUTS` (Middle ≥ 0, Senior ≥ 1): разница больше SE — «предложить новый порог», и показывается,
  какая доля кандидатов при стандартном нормальном распределении сменила бы грейд. Порог меняет владелец, автоматически — нет.
  Параметры заданий пока — экспертная предкалибровка; после калибровки на людях пороги пересчитаются по новым параметрам.

Проверка расчёта: та же цепочка на синтетической разметке с заложенной истиной (пороги θ 0,2 и 1,15, точная и внушаемая модели) —
блок «Проверка расчёта на синтетической разметке» на `/validation` и `python -m app.modules.experts synth-check`.

## 8а. Пакет v2 (вторая волна, только задание A)

Зачем: в v1 размечено 109 пар по 10 потребностям — на таком объёме разница подбора с BM25 не значима. v2 добавляет ≈ 200 новых
пар по всем демо-потребностям текущего мира. Блоки B и C в v2 не входят, пакет v1 и его оценки не меняются.

**Состав** (`backend/app/modules/experts/pack2.py`). Потребности — N00–N16 (как создаёт `demo.seed`: 15 основных и 2 стажёрские) и
J00–J02 из песочницы жюри (добавляются, пока объём ≤ 240 пар). Пул — только демо-кандидаты, видимые работодателю (персоны жюри и
живые пользователи не входят). На потребность:

- топ-8 подборки match-v1 — тот же отбор и порядок, что `ranking.build_selection` (ярус статуса грейда → скор → рейтинг → ref);
- 3 случайных из мест 9–30 подборки;
- 2 «трудных отрицательных»: случайно из той же категории вне топ-30 (места 31+); если их меньше двух — из соседних грейдов
  того же направления, затем из остального направления (у стажёрских потребностей подборка из 2 кандидатов — пул 4 пары).

Пары, совпавшие с v1 (та же потребность по тексту и тот же кандидат), заново не размечаются: после `demo.seed --reset` ref
кандидатов случайны, поэтому совпадение ищется по отпечатку снимка карточки (категория, θ, погрешность, стаж, город, формат).
Такая строка v2 хранит ключ v1 (`hidden.borrowed_from`), её эталон в метриках v2 — оценки v1. Зерно фиксировано (20261008),
кадры выборки упорядочены по номеру демо-кандидата — сборка детерминирована; повторный `build` ничего не меняет.

**Назначение.** Каждая потребность целиком — паре ролей (E1+E2, E1+E3 или E2+E3), жадно по нагрузке; каждая новая пара — двум
ролям, на роль ≤ 160. Роли v2 — отдельные участники панели пакета v2 (коды те же, E1–E3; ссылки-приглашения нет, разметка —
офлайн файлами). Порядок объектов перемешан по роли.

**Карточка вслепую** — как в v1: без места, баллов, названия метода и ref; у кандидата без подтверждённого грейда — статус и
заявленный грейд. Экспорт: `item_id`, номер, потребность, карточка текстом (`card_text`) и полями (`card`), вопрос, шкала 0–3,
правила, формат ответа. Скрытые поля (места match-v1 и BM25, страта, разметка по правилам) остаются в базе.

**Импорт.** Строка ответа: `{"item_id": "…", "relevance": 0–3, "comment": "…", "must_have_missing": "…"}` (принимается и формат
файлов v1 с `value`). Те же проверки, что в кабинете эксперта (целое 0–3, комментарий до 2000 знаков, объект — из назначения
роли); всё или ничего: при любой ошибке не записывается ничего. Повторный импорт того же файла ничего не дублирует, изменённые
оценки перезаписываются. Источник указывается честно (`--source people|model`, для модели — `--model`); смешать источники под
одним кодом нельзя.

**Как считаем** (`analysis.matching_by_pack`, `/validation#experts`, блок «Пакеты v1 и v2»). Эталон пары — медиана оценок,
релевантна от 2. По снимку пакета (места сохранены при сборке, от текущих id не зависят) для v1, v2 и вместе:

- P@5 и nDCG@10 (gain 2^rel − 1, идеальный DCG — по всем размеченным парам пула) match-v1 и BM25. Топ-5 match-v1 размечен
  полностью в обоих пакетах. BM25 — сжатый список (Sakai, 2007): упорядочивает только размеченные пары пула своей потребности.
  В v2 пул собран по подборке match-v1, поэтому BM25 получает категорийный фильтр даром — разность консервативна (доля его
  собственного топ-5 в пуле показывается). Чувствительность — допущение TREC «неразмеченные = нерелевантны» (оно строже к BM25);
  истинная разность — между двумя оценками.
- Разность match-v1 − BM25 — 95 % ДИ бутстрепа по потребностям (2000 повторов; в «v1 + v2» одна и та же потребность из двух
  пакетов — один кластер) и знаковый критерий Уилкоксона.
- Согласие — квадратично взвешенная каппа (среднее по парам ролей) и порядковая альфа Криппендорфа с 95 % ДИ.
- Если разметку делала модель — подпись «Модельная разметка по экспертному протоколу, не люди» с названием модели.

Пока v2 не размечен, раздел показывает v1, как раньше. Проверка расчёта — `backend/tests/test_experts2.py` (на синтетике с
известным ответом ДИ накрывает истинную разность и сужается с ростом числа потребностей).

```bash
# на сервере, из каталога проекта
docker compose exec api python -m app.modules.experts pack2 build --dry-run    # состав без записи: пары, роли, совпадения с v1
docker compose exec api python -m app.modules.experts pack2 build              # собрать (повторно — ничего не делает)
docker compose exec -T api python -m app.modules.experts pack2 export --code E1 --out - > v2_E1.jsonl   # так же E2, E3
docker compose exec -T api python -m app.modules.experts pack2 import --code E1 --file - \
    --source model --model "Claude Fable 5.1" --role "тимлид Backend" < v2_E1_labels.jsonl
docker compose exec api python -m app.modules.experts pack2 status             # объём и прогресс ролей v2
```

## 9. Что публикуется

На `/validation` — только агрегаты и коды E1–E3 с прогрессом, без имён и без текстов оценок. Если согласие ниже порога — публикуем
как есть и разбираем, на каких парах и ответах расходятся.

## 10. Для координатора

```bash
# на сервере, из каталога проекта
docker compose exec api python -m app.modules.experts pack                     # собрать пакет (иначе соберётся при первом заходе)
docker compose exec api python -m app.modules.experts invite E1 --name "Имя" --profile "тимлид Backend"   # --team 2, если экспертов двое
docker compose exec api python -m app.modules.experts invite E1 --rotate       # новая ссылка, старая перестаёт работать, оценки сохраняются
docker compose exec api python -m app.modules.experts status                   # прогресс и пометки «одинаковые оценки»
docker compose exec api python -m app.modules.experts llm-grade                # оценки моделей на ответах B (нужен LLM)
docker compose exec api python -m app.modules.experts synth-check              # проверка расчёта на синтетике
```

Ссылка печатается один раз, в базе — только её хеш. Создать приглашение можно и через API администратора: `POST /api/expert-panel/invites`.
