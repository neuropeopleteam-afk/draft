## Вывод (честно)
- На их формате наш продукт **заметно ниже** их ранжировщика по всем метрикам обоих протоколов (ДИ разности целиком
  ниже нуля) и ниже их простой базовой линии «поиск по резюме». Перевод полей (B) лучше «как есть» (A) — продукт
  использует результат теста и подтверждённые навыки, если их передать.
- Почему (разбор по РАЗРАБОТКЕ, `dev_matching.json`): (1) строгий фильтр по одному грейду — вакансия «Junior / Middle»
  получает один грейд, а соседний грейд в их метках часто релевантен; (2) у них 8 направлений, у нас 5 — мобильные,
  DevOps и аналитики попадают в чужие направления (по умолчанию backend/frontend/data_ml); (3) их метки построены их
  моделью релевантности; (4) часть их подтверждённых навыков (System Design, Микросервисы, Сети, DOM, Web API и др.) не имеет пары в нашей онтологии из 64 тегов.
- Разбор резюме: e-mail и телефон — 1,000; по навыкам строго в их онтологии F1 0,713 (их онтология шире: 120 навыков),
  на общей части онтологий полнота 0,963; направление на общих направлениях — 1,000. GitHub и город продукт в ответе
  загрузки не выдаёт. Их «текущий» результат на отложенном получен после правок по нему же; их честная отложенная цифра —
  «до правок» (F1 0,937).
- Для сайта эту оценку как «победу» не использовать. Как пример честной процедуры: продукт проверен на чужом открытом
  формате с чужими метриками, протокол и хэши заморожены до единственного прогона, результат опубликован как есть.
- Находки для подбора (переданы А5): алиасы меток `vacancy/candidate` в загрузке набора, вакансии с двумя грейдами,
  «вне направлений» вместо backend по умолчанию, Telegram из ссылки t.me.
