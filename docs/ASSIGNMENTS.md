# Задания работодателя: автопроверка, причина предложения, рубрика

Модуль `backend/app/modules/assignments`, кабинеты — `frontend/src/pages/assignments`. Первый этап (И7) собирает 3–5 заданий банка
по стеку потребности или вакансии; второй (К5) делает предложения адресными: система объясняет, почему именно это задание, показывает
рубрику оценки до и после, учитывает результат в свежести профиля и в строке объяснения подборки.

## Как это работает

1. **Источник.** Работодатель собирает задание из потребности, вакансии или по стеку вручную. Банк даёт по 3–5 семейств заданий
   нужной сложности; ключи вариантов остаются на сервере, код кандидата не исполняется.
2. **Куда уходит.** Три режима: `probe` (лично выбранным кандидатам), `vacancy` (откликнувшимся), `open` (в ленту «Задания для вас»).
3. **Причина предложения («почему вам»).** При выдаче сохраняется слепок причины (`assignment_attempts.why`) — виден и кандидату,
   и работодателю. Причины по убыванию веса (модуль `why.py`; тексты детерминированы, нейросеть не используется):

   | Причина | Условие | Вес |
   |---|---|---|
   | `weak_skill` | навык из стека задания подтверждён слабо (доля верных ниже 50 %) | 1,0 |
   | `stale_skill` | навык подтверждался больше 180 дней назад / больше 90 дней назад | 0,9 / 0,6 |
   | `declared_only` | навык заявлен в опросе, на платформе не подтверждён | 0,5 |
   | `need_match` | стек задания пересекается с обязательными требованиями потребности или вакансии | +0,3 × доля обязательных у кандидата |
   | свежий навык | уже подтверждён за последние 90 дней | 0,1 |

   Для выбора открытого задания в ленте вес предложения = сумма весов причин по стеку задания + 0,25, если грейд задания совпадает
   с грейдом кандидата. Работодателю тексты показываются нейтральными: «навык … требует подтверждения», без слов «заявлен в опросе» и без
   цифр слабого результата — заявленный стек остаётся приватным.
4. **Рубрика (`rubric.py`).** 100 баллов. Без просьбы о подходе: «Верные ответы» 70 + «Покрытие стека» 30, всё считает система.
   С просьбой описать подход: 50 + 20 автоматически, «Подход к решению» 20 и «Риски и проверка результата» 10 ставит работодатель по
   описанным уровням (0/5/10/15/20 и 0/5/10, у каждого уровня — якорь словами). Рубрика сохраняется в задании, шаблон можно менять без
   влияния на выданное. Кандидат видит её до старта, работодатель — до создания (предпросмотр) и после.
   Текст подхода (2–2000 символов, не меньше 40) очищается от контактов, ссылок и ФИО локальными правилами (`resume.pii.redact`, без нейросети)
   до записи в базу.
5. **Результат и оценка.** После отправки система считает автоматические баллы. Если в рубрике есть критерии работодателя, попытка получает
   `review_status=pending`: в подборке виден результат автопроверки с пометкой «оценка подхода ожидается». Работодатель выбирает уровень по
   каждому критерию (`POST …/attempts/{id}/review`), итог = автобаллы + баллы работодателя; кандидат получает письмо и push. Оценку можно
   исправить; даты подтверждения навыков при этом не сдвигаются.
6. **Что меняется в профиле.** Факты навыков T1 (`kind=skill`) пишутся по автопроверке сразу (результат ниже 50 % навык не подтверждает, но
   обновляет дату). Факт «зонд» (`kind=probe`, `value.origin=assignment`) до оценки несёт долю верных, после — итог рубрики / 100.
   Вес компонента «зонд» в match-v1 (0,05) и формула не менялись: порядок подборки определяется прежними компонентами.
7. **Строка в подборке.** Блок «Зонд» в объяснении показывает только собственные зонды; адресное задание — отдельная строка «Адресное
   задание» (T1): название, дата, итог рубрики с разбивкой «автопроверка / оценка работодателя» или «оценка ожидается», перечень проверенных
   навыков. Тест `test_ranking_signal_present_and_order_unchanged` проверяет, что порядок и скоры одинаковы с этой строкой и без неё.

## Свежесть профиля (`profiles/freshness.py`)

Для каждого навыка T1 берётся дата самого позднего подтверждения (тест или задание). До 90 дней — «свежо», 91–180 — «стареет», дальше —
«давно»; пороги заданы заранее и на данных не подбирались. Сводка: доля свежих подтверждённых навыков ≥ 0,7 — «Свежий», ≥ 0,4 —
«Частично устарел», иначе «Давно не обновлялся». Кандидат видит панель с датами; работодатель — строку в карточке по подтверждённым
навыкам (слабые не показываются, как и раньше). Свежесть объясняет, но не меняет порядок подбора.

## Периодичность, лимиты, напоминания (`feed.py`)

| Параметр | Значение | Настройка |
|---|---|---|
| Интервал между предложениями ленты | 7 дней; кандидат выбирает 7 / 14 / «не предлагать» | `assignments_feed_days`, `PUT /candidate/assignments/prefs` |
| Одно активное предложение | пока не решено, не отклонено и не истекло, новое не приходит | — |
| Лимит | не больше 4 предложений за скользящие 30 дней | `assignments_feed_monthly_limit` |
| Отступление | после двух подряд отказов/истёкших интервал ×2 | — |
| Срок предложения | 14 дней, затем «Предложение истекло» (без последствий для рейтинга) | `assignments_offer_ttl_days` |
| Напоминание кандидату | через 2 дня без начала, до двух раз | `assignments_remind_days` |
| Напоминание работодателю об оценке | через 3 дня после отправки, до двух раз | `assignments_review_remind_days` |

Запуск: лениво при открытии списков, фоновым потоком раз в час (`assignments_feed_interval_s`) и вручную: `python -m app.modules.assignments.feed`.

## Песочница жюри

Работодатель «Северный платёж» получает четыре задания: зонд с подходом (Мария — решено и оценено, видно «до» и «после»; Илья — подход
ждёт оценки, напоминание отправлено), задание к вакансии (Илья), открытое задание Марии (причина — навык, давно не подтверждавшийся;
напоминание уже отправлено) и открытое задание для Junior Артёму (причина — слабые навыки). У Марии даты навыков из теста Backend заданы 130 днями
раньше — только в песочнице, чтобы свежесть была видна сразу. Кнопка «Смоделировать неделю» (только песочница, `POST
/candidate/assignments/demo/next-week`) сдвигает даты ленты на период и запускает обычный цикл: первый клик — напоминание, второй — истечение
и новое предложение с причиной.

## API

Кандидат: `GET /api/candidate/assignments` (элементы с `why`, `rubric`, `review_status`; `schedule`, `freshness`), `PUT …/prefs`,
`POST …/demo/next-week`, `POST …/{id}/start|submit|decline` (`submit` принимает `approach`). Работодатель: `POST /api/employer/assignments`
(`with_approach`, `approach_prompt`), `POST …/preview` (`rubric`, `rubric_auto`, `approach_prompt`), `POST …/{id}/attempts/{attempt}/review`
(`{scores: {criterion: points}, comment}`). Схема — `/api/docs`.

## Ограничения

- Автоматически оцениваются только ответы по заданиям банка и покрытие стека; качество подхода оценивает человек. Нейросеть в проверке не участвует.
- Подбор причины опирается на факты T1/T0 профиля и требования потребности; для навыков без заданий в банке причины «слабо/давно» не строятся.
- Порог слабого навыка 0,5 и пороги свежести 90/180 дней — договорённость системы, а не результат подбора на данных.
- Миграция `tk02` добавляет колонки и таблицу `assignment_prefs`; обратная миграция удаляет их вместе с данными К5.
