# Тестирование и CI

Коротко: 109 автотестов бэкенда (SQLite и PostgreSQL 16, покрытие строк 84 % при пороге 80 %), валидатор
банка из 128 семейств заданий (1113 проверок ключей исполнением кода, ошибок 0), проверка типов и сборка

Цифры ниже — прогон 6 октября 2026 г. на общей машине (2 ядра, параллельно работали другие сборки), поэтому

## Что проверяем и зачем (связь с критериями ТЗ)

Веса критериев: подбор 35 %, тестирование 25 %, интерфейс 10 %, питч 10 %, техника 7 %, доп. функции 7 %,
полнота и документация 6 %.

### Подбор (35 %)

- `test_day2_rules.py` (21 тест): потребность разбирается без LLM (`need_parser_without_llm`), подборка
  версионируется и объясняет каждого кандидата (`need_selection_versions_and_explanations`), самоописание T0 не
  влияет на балл (`t0_does_not_affect_score`), карточка обезличена и контакты скрыты до согласия
  (`card_is_anonymous_and_contacts_hidden_until_accept`), вилка зарплаты обязательна, лимит приглашений 30 дней,
  кандидат видит только свои приглашения, снятие публикации прячет профиль.
- `test_day3a.py`: требования «обязательно / будет плюсом», зарплата «на руки» и односторонняя вилка, метрики
  ранжирования (nDCG, Precision), базовая линия BM25, атаки «красной кнопки» (раздувание резюме, смена имени,
  фальшивый и убранный значок ФСП, утечка банка).
- `test_integrations.py`: индекс доверия работодателя по ЕГРЮЛ виден в приглашении, ликвидированная компания —
  низкое доверие, мягкая деградация при капче реестра; выгрузка в ATS и вебхук при принятии приглашения.
- E2E `02-employer-invite.spec.ts`: работодатель пишет потребность текстом → разбор (направление, грейд, теги,
  вилка) → подборка с блоком «Почему в подборке» → обезличенная карточка → приглашение-оффер (без верхней границы
  вилки отправить нельзя) → кандидат принимает → работодатель видит контакты.
- E2E `03-validation-red-button.spec.ts`: на странице /validation есть метрики подбора (nDCG, BM25), каждая из
  пяти атак «красной кнопки» показывает «Свойство выполнено» и ничего не записывает.

### Тестирование кандидата (25 %)

- `test_bank_engine.py` (9): адаптивная сессия на банке заданий, сильный кандидат подтверждается, слабый — нет,
  дотестирование у порога, ключи и seed не попадают в публичную часть, открытый ответ без LLM уходит на проверку,
  чужой токен и неверный шаг отклоняются, полный проход через API.
- `test_day3a.py` (29): контроль частоты показа заданий (Sympson — Hetter) и ротация субпулов при пересдаче,
  лимиты форматов, уровни достоверности результата (античит) и очистка сигналов, проверка экспертом, одинаковая
  фиксированная форма для всех.
- `test_day2_rules.py`: правило 90 дней и обход для демо жюри, неподтверждение не понижает категорию, без опроса
  к тесту не пускает, зонд создаёт факт T1.
- Валидатор банка (`tools/ci/check_bank.py` → `backend/assessment_bank/validator.py`): на каждом из 128 семейств
  20 seed — детерминизм (в процессе и в отдельном процессе), уникальность и разнообразие вариантов, позиция
  правильного ответа не угадывается, инварианты (длина кода, число операций, тип дефекта); на 3 seed ключ
  проверяется исполнением кода в песочнице (Python, JavaScript, bash, git, SQLite). FAIL или ошибка ключа валят
  сборку, WARN — нет.
- E2E `01-candidate-test.spec.ts`: демо-вход кандидатом → «Тест на грейд» → ответы на все задания до остановки
  (в прогонах 23 ответа: выбор варианта, строка кода, вывод программы, текст) → результат с θ и числом оценённых
  заданий → переход к категории, место в категории, правило 90 дней.

### Интерфейс (10 %)

- `test_ui_contract.py`: поля, которые читают страницы кабинетов, есть в ответах API на всём пути
  кандидат → работодатель → приглашение → контакты.
- Все 6 сквозных сценариев идут через настоящий интерфейс в Chromium (1366×900, ru-RU) по ролям и подписям
  элементов, как их видит пользователь: если пропадёт кнопка или подпись, тест упадёт.

### Техника и доп. функции (7 % + 7 %)

- `test_auth.py`, `test_security_day3a.py`, `test_me.py`: регистрация с кодом, Argon2, блокировка после неверных
  кодов, ограничение перебора пароля, разделение ролей, эксперт жюри не администратор.
- `test_access_matrix.py` (+ `route_walk.py`, `security_policy.py`): матрица прав. Тест обходит все маршруты FastAPI
  (186 на 07.10, включая вложенные роутеры и статику) для 13 ролей — аноним, кандидат, работодатель своей и чужой
  компании, админ, аналитик ФСП, эксперт, четыре персоны песочницы жюри A и две персоны песочницы B — и сверяет ответ с
  именованной политикой маршрута (`open`, `auth`, `candidate_own`, `employer_ref`, `admin`, `expert`, `fsp`,
  `jury_demo` и др.). Маршрут без политики роняет тест и печатает готовую строку для `POLICY`; новые ветки добавляют
  строки (инструкция — в докстринге `security_policy.py`). Около 80 с, 2 418 запросов. Калибровка нашла настоящую
  дыру: кубки, созданные через API работодателем песочницы, были видны кандидатам других песочниц.
- `test_sandbox_isolation.py`: две песочницы жюри, общее демо, настоящие работодатель и кандидат — карточка кандидата,
  PDF, сравнение, зонды и приглашения по `ref`, вакансии и кубки, созданные через API, не пересекаются; каждая
  проверка проверена откатом правки (200 вместо 404). `test_security_day3a.py::test_k2…` берёт маршруты `/api/admin/*`
  обходчиком, требует непустой список и проверяет их экспертом жюри и анонимом.
- `test_integrations.py`: ФСП ID (OIDC + PKCE, проверка подписи id_token, согласие, паспорт T2), Хантфлоу,
  подпись вебхуков и защита от SSRF, push-уведомления, анкета SUS.
- `test_cup.py`, `test_fsp_cabinet.py`: Кубок работодателя (автопроверка и рубрика, оценка вслепую, итоги,
  приглашения лучшим с вилкой кубка, запись в паспорт ФСП как T1) и Кабинет ФСП (группы меньше 5 скрыты, нет
  персональных данных в отчёте и CSV); у каждой песочницы жюри свои кубки, аналитика ФСП не меняется от числа
  песочниц, сброс одной песочницы не трогает другую.
- `test_migrations.py`: модели совпадают с миграциями; в CI на PostgreSQL ещё прогоняются миграции вверх до head
  и обратно до base на чистой базе.
- `test_config_env.py`: `.env`, созданный `make env` из `.env.example`, запускает API (пустые значения — как
  незаданные). Ошибку нашла сквозная проверка стека: с пустым `DEV_MODE=` контейнер api не стартовал.
  Там же найдена гонка при первом запуске с чистым томом: проверка готовности db отвечала «готов» ещё на
  временном сервере init-скриптов, api падал на миграциях, и `docker compose up --wait` завершался ошибкой.
  Теперь проверка идёт по TCP (`pg_isready -h 127.0.0.1`), CI поднимает стек всегда с чистой базой.
- Docker: сборка образов api, web и keycloak (профиль fsp-id), запуск стека до healthcheck, демо-данные и дымовая
  проверка `tools/ci/stack.sh smoke` (сайт, SPA-маршрут, API, OpenAPI, каталог, режим жюри, отчёт валидации,
  миграции на head, вход жюри).

### Полнота и документация (6 %)

- `actionlint` (с shellcheck внутри шагов), `shellcheck` скриптов, `docker compose config` для основного стека и
  профиля fsp-id; этот документ и значки в README.

## Сквозные сценарии (папка e2e/)

Отдельный пакет со своим `package.json` (Playwright 1.63, TypeScript), фронтенд не затрагивает.

| Файл | Сценарий |
|---|---|

| `tests/02-employer-invite.spec.ts` | потребность текстом → разбор с цитатами → подборка с объяснениями → приглашение с вилкой; кандидат принимает → контакты → журнал передач в ATS (Talantix, «Поток», Хантфлоу, вебхук) |
| `tests/03-validation-red-button.spec.ts` | главная → «Красная кнопка»; /validation: все разделы, бенчмарк со скрытой истиной, условия конкурентов, экспертная разметка; шесть атак, включая «пол, возраст и имя» |
| `tests/04-need-art64-compare.spec.ts` | пример с нарушением ст. 64 → цитаты и предупреждение → «Переписать через навыки» → подборка → сравнение трёх кандидатов |
| `tests/05-invitation-complaint.spec.ts` | жалоба кандидата на приглашение → отклонено, индекс доверия учитывает жалобу, работодатель видит причину без комментария |
| `tests/06-cup-fsp.spec.ts` | кубок: оценка решений по рубрике → итоги → приглашения топ-3; место кандидата в кубке; Кабинет ФСП: период, разделы, CSV |
| `tests/07-expert-labeling.spec.ts` | вход эксперта, демо-назначение → оценка в заданиях A, B, C → прогресс |
| `tests/08-mobile-390.spec.ts` | ширина 390 px: ключевые экраны всех ролей, снимки, проверка горизонтальной прокрутки |

Песочницы жюри. Один прогон = одна своя песочница: `global-setup.ts` входит с `scenario: "new"` и получает
id песочницы, все демо-персоны прогона (кандидаты, работодатель, эксперт, ФСП) — её учётки. Браузер получает id
в localStorage (`jury_scenario`), как у эксперта жюри после входа в один клик, поэтому кнопки «Войти как …» на
главной ведут в неё. В конце `global-teardown.ts` сбрасывает только её (`POST /api/jury/reset` с токеном её
персоны). Общее демо и песочницы других экспертов жюри тесты не трогают; если стенд вместо песочницы пустил в
общее демо (лимит — 12 новых песочниц в час с адреса), прогон останавливается с ошибкой. `E2E_SCENARIO=<id>` —
продолжить свою песочницу (перед прогоном она сбрасывается), `E2E_KEEP_STATE=1` — не сбрасывать после прогона.

Известные ошибки продукта. Проверка, которая упирается в уже найденную ошибку приложения (`productIssue` в
`lib/fixtures.ts`), не валит прогон, а пишет аннотацию «ошибка продукта» — она попадает в сводку
(`scripts/summary.mjs`). `E2E_STRICT=1` — такие проверки валят тест.

Сеть до стенда. Из нашей песочницы до сервера в Москве заметная доля соединений с крупным ответом
обрывается после первых ~16 КБ (с самого сервера те же файлы отдаются без сбоев). Чтобы сценарии проверяли
приложение, а не канал, для удалённого стенда `lib/net.ts` пропускает GET-запросы через повтор с тайм-аутом и
держит неизменяемые файлы сборки в памяти на время прогона; POST и прочие запросы уходят из браузера как есть и
один раз. Против локального стека слой выключен (`E2E_NET_RETRY=1|0` — принудительно). В конце прогона печатается
статистика повторов.

Снимки экранов 390 px — `reports/mobile` (`E2E_SHOTS_DIR` — другая папка). Отчёты: `e2e/reports/html` (HTML-отчёт Playwright, `npm run report`), `reports/junit.xml`,
`reports/results.json`; при падении — скриншот, видео и трассировка в `reports/artifacts`.

## Как запустить

Бэкенд (Python 3.12, зависимости `backend/requirements.txt` и `requirements-dev.txt`):

```bash
cd backend
python -m pytest -p no:cacheprovider                                   # SQLite, ≈ 1 мин
python -m pytest -p no:cacheprovider --cov=app --cov-report=term:skip-covered --cov-report=xml:coverage.xml
TEST_DATABASE_URL=postgresql+psycopg://fsp:fsp@localhost:5432/fsp_test python -m pytest -p no:cacheprovider
python ../tools/ci/check_bank.py --seeds 20 --verify-seeds 3 --out /tmp/bank_report   # банк, ≈ 2 мин
```

Или через make: `make test`, `make test-pg` (в Docker), `make coverage` (обновляет `docs/badges/*.svg`),
`make test-bank`.

Фронтенд: `cd frontend && npm ci && npm run typecheck && npm run build`.

Стек и сквозные сценарии локально:

```bash
tools/ci/stack.sh up && tools/ci/stack.sh seed && tools/ci/stack.sh smoke    # или make stack-ci
cd e2e && npm ci && npx playwright install chromium
E2E_BASE_URL=http://127.0.0.1:8140 npx playwright test                      # или make e2e
tools/ci/stack.sh down                                                       # остановить и удалить тома
```

Против стенда (пароль базовой авторизации — в README, раздел «Доступ к стенду»):

```bash
cd e2e
E2E_BASE_URL=https://fsp.neuropeople.pro E2E_BASIC_USER=demo E2E_BASIC_PASSWORD=… npx playwright test
```

Линтер workflow: `actionlint` из корня репозитория.

Проверки безопасности (те же, что в задании `security` CI; журнал последнего локального прогона —
[docs/ci/security_run_0810.md](ci/security_run_0810.md)):

```bash
gitleaks git --no-banner --redact=100 --config .gitleaks.toml .          # секреты в истории, gitleaks 8.28.0
gitleaks dir --no-banner --redact=100 --config .gitleaks.toml .          # секреты в рабочем дереве
cd backend && python -m venv /tmp/app && /tmp/app/bin/pip install -r requirements.txt -r requirements-dev.txt
pip-audit --strict --progress-spinner off --path /tmp/app/lib/python3.12/site-packages        # окружение с транзитивными
pip-audit --strict --progress-spinner off --no-deps --disable-pip -r requirements.txt -r requirements-dev.txt
pip-audit --strict --progress-spinner off --no-deps --disable-pip -r assessment_bank/BANK_requirements.txt
cd ../frontend && npm audit --omit=dev --audit-level=high               # production-зависимости, порог high
```


## CI в GitHub Actions

`ci.yml` — на каждый push в main, pull request и вручную; задания идут параллельно:

| Задание | Что делает |
|---|---|
| Workflow, скрипты, compose | actionlint 1.7.12, shellcheck, `docker compose config` (основной стек и fsp-id) |
| Безопасность · секреты · уязвимости | gitleaks 8.28.0 по истории и дереву (исключения с обоснованием — `.gitleaks.toml`), pip-audit 2.9.0 (окружение бэкенда с транзитивными, пины requirements и банка заданий), `npm audit --omit=dev --audit-level=high`; SARIF-отчёты gitleaks — в артефактах, сводка npm audit по всем зависимостям — на странице запуска |
| Бэкенд · SQLite · покрытие | pytest с покрытием; порог `fail_under = 80` в `backend/pyproject.toml`; JUnit, HTML-отчёт, значки — в артефактах, сводка — на странице запуска |
| Бэкенд · PostgreSQL 16 | service-контейнер postgres:16-alpine; миграции вверх и вниз на чистой базе; те же тесты |
| Банк заданий · валидатор | `tools/ci/check_bank.py`; отчёт JSON и Markdown в артефактах |
| Фронтенд · типы · сборка | `npm ci`, `npm run typecheck`, `npm run build`, размеры файлов в сводке |
| Docker-образы · стек · e2e | вызывает `e2e.yml` с target=local: сборка api, web и keycloak, стек, демо-данные, дымовая проверка, сценарии Playwright; при падении — логи контейнеров |

`e2e.yml` — сквозные сценарии против стенда вручную (выбор target: stand или local и адреса) и каждую ночь в
02:30 по Москве. Нужен секрет репозитория `E2E_BASIC_PASSWORD`; логин — переменная `E2E_BASIC_USER` (по
умолчанию demo). Ночной прогон выключается переменной `E2E_STAND_SCHEDULE=off`. Одновременно против стенда
идёт не больше одного прогона.

Действия GitHub закреплены по SHA коммита (рядом указана версия), права токена — только чтение.

Значки в README — SVG из `docs/badges`, их пересчитывает `make coverage`; в CI свежие значки лежат в артефакте
задания SQLite. Значок статуса GitHub Actions добавляется в README после публикации репозитория.

## Чего тесты не покрывают

- Модули с низким покрытием: `validation/__main__.py` (0 %, это пересчёт метрик /validation, его проверяет сам
  результат на странице), `validation/matching_eval.py` (31 %), `llm/client.py` (35 %: в тестах LLM выключен),
  `validation/sim.py` (39 %), `assessment/grader.py` (40 %), `resume/extract.py` (53 %), `egrul/client.py` (58 %:
  живой реестр в тестах не вызывается).
- Сквозные сценарии отвечают на задания «вслепую» (ключи на клиент не попадают), поэтому проверяют механику теста и
  неподтверждение без понижения категории, а не успешное подтверждение грейда — его проверяет
  `test_bank_engine.py::test_strong_candidate_confirmed_adaptive_and_canaries`.
- Нагрузочное тестирование — отдельно, `docs/LOAD_TEST.md`.
