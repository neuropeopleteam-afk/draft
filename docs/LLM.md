# LLM: цепочка моделей

Код: `backend/app/modules/llm/client.py` (цепочка, автомат-выключатель, ретранслятор, провайдер `local` — своя
открытая модель, раздел 9), `assessment/grader.py`
(оценка открытых ответов, вторая оценка), `matching/need_parser.py` (разбор потребности), `resume/extract.py`
(резюме), `resume/pii.py` (вырезание ПДн). Тесты — `backend/tests/test_llm_chain.py` (подменённый транспорт httpx,
без сети). Прогоны — `tools/llm/`, результаты — `docs/llm/`.

## 1. Какая модель где и почему

| Функция | Цепочка (сервер, `LLM_CHAIN=openrouter,yandex`) | Тайм-аут | Рассуждения | Почему |
|---|---|---|---|---|
| `parse_need` — разбор вакансии | Claude Sonnet 5.5 → yandexgpt-5.1 → правила | 25 с | low | Sonnet: лучшая полнота стека среди ответивших на все 50 вакансий, 2,7 с; yandexgpt-5.1 — самая быстрая и надёжная запасная (раздел 6) |
| `resume` — разбор резюме (после вырезания ПДн) | Claude Sonnet 5.5 → yandexgpt-5.1 → словари | 25 с | low | та же задача извлечения, тот же выбор |
| `grade` — оценка открытого ответа | Claude Sonnet 5.5 → `LLM_GRADING_MODEL` (Yandex) → «на проверке» | 40 с | по умолчанию модели | на наборе оценщика: 0 из 116 атак проходят, порядок сильный > средний > слабый на 29 из 29 заданий, 2,7 с |
| `grade_second` — вторая оценка спорных | Claude Fable 5.1 → `LLM_GRADING_MODEL` → эксперт | 40 с | low | другая модель (независимая ошибка); вызывается для 16 % ответов (раздел 4) |

Профиль `llm-local` (`make llm-local`, `LLM_CHAIN=local`, раздел 9) — для машины без GPU и без зарубежных API:

| Функция | Профиль `llm-local` | Тайм-аут | Почему |
|---|---|---|---|
| `grade`, `grade_second` | Qwen3.5-9B Q4_K_M на CPU (вторая оценка — та же модель) | 50 с, бюджет 50 с | 0 из 116 атак, MAE к эталону 0,147 / 0,129; на CPU ≈ 27 с на ответ |
| `parse_need`, `resume` | правила и словари (`LLM_MODEL_<FUNC>=off`) | — | на 50 вакансиях Qwen снижает F1 стека (0,87 против 0,91) и выдумывает требования к опыту; 29 с на CPU |

Режим «только российская модель» (`LLM_CHAIN=yandex`, все функции — YandexGPT 5.1 в Yandex AI Studio) — раздел 11:
как включить и замер против Sonnet и правил на одних входах.

Без новых переменных поведение прежнее: один провайдер `LLM_*` (Yandex AI Studio), модель `LLM_MODEL`, оценка —
`LLM_GRADING_MODEL`, второй оценки нет (та же модель — не независимая).

Последний рубеж у каждой функции — путь без LLM: словарь стек-тегов и правила (разбор), статус «на проверке» и
эксперт (оценка). Интерфейс показывает, какая модель фактически ответила: «разбор: словарь + Claude Sonnet 5.5,
цитаты проверены», при переходе — имя запасной, если не ответил никто — «разбор по словарю: модель не ответила».
Цитата из вакансии подписана моделью, которая её нашла. В журнале проверки (экран эксперта) — обе оценки с именами
моделей.

## 2. Цепочка и автомат-выключатель

- Порядок — `LLM_CHAIN` (`openrouter,yandex`; провайдер без ключа пропускается). Переход к следующему: ошибка
  сети, тайм-аут, HTTP ≠ 200, ошибка в теле ответа, пустой ответ, невалидный JSON, ответ не прошёл проверку
  вызывающего (`validate`: например, у оценки нет балла по всем критериям). Причины — в `attempts` результата.
- Разбор JSON терпим к «поправкам»: если модель вывела объект, затем «Поправка: …» и второй объект — берётся
  последний целый объект; обрезанный ответ остаётся невалидным (переход дальше), внутренние объекты не берутся.
- Автомат-выключатель на пару «провайдер:модель»: `LLM_BREAKER_FAILURES` ошибок подряд (3) → пропуск
  `LLM_BREAKER_COOLDOWN_S` секунд (60), затем одна пробная попытка; успех закрывает автомат, ошибка — снова открывает.
  Недоступная модель второй оценки не выключает основную модель того же провайдера. `0` — автомат выключен.
- Модель, тайм-аут и усилие рассуждений — на функцию: `LLM_MODEL_<FUNC>` (`модель` — для первого провайдера цепочки
  или `openrouter=…,yandex=…`), `LLM_TIMEOUT_<FUNC>`, `LLM_REASONING_<FUNC>` (`low | medium | high | default`).
  У Sonnet 5.5 рассуждения не выключаются (HTTP 400), поэтому `low`: на длинной вакансии с рассуждениями по умолчанию
  827 из 1200 токенов ушли на рассуждения и JSON обрезался; с `low` — 0 токенов рассуждений, ответ вдвое дешевле.
- Общий бюджет оценки одного ответа — `LLM_GRADING_BUDGET_S` (50 с): первая и вторая оценка с переходами по цепочке
  укладываются в `proxy_read_timeout` nginx (60 с), ответ кандидата ждёт оценку синхронно. Не хватило времени на
  вторую оценку — ответ «на проверке» (повтор при завершении теста, затем эксперт).
- `/api/meta` → `llm`: `chain` (провайдеры, настроен ли, через ретранслятор ли), `functions` (модели по порядку,
  тайм-аут), `breaker` (открытые автоматы), `last` (кто ответил последним по функции и был ли переход). Ключей,
  адреса ретранслятора и каталога Yandex Cloud там нет; прежние поля `configured`, `provider`, `model` сохранены.

## 3. OpenRouter и ретранслятор

- Ключ — `OPENROUTER_API_KEY` (файл `OPENROUTER_ENV_FILE`, на сервере `/opt/spectrek_fsp/secrets/openrouter.env`).
  Заголовки атрибуции нейтральные: `HTTP-Referer: https://localhost`, `X-Title: llm-client` — без названия
  продукта и домена (тест). В теле — `provider.data_collection = deny` (провайдеры, хранящие запросы для обучения,
  исключаются).
- Ретранслятор: OpenRouter определяет страну исходного запроса, с сервера в РФ — 403. Если задан `LLM_RELAY_URL`,
  клиент ходит на него (базовый адрес OpenAI-совместимого API уже с `/api/v1`, клиент добавляет
  `/chat/completions`) и добавляет `X-Relay-Token: LLM_RELAY_TOKEN`; ключ OpenRouter — в `Authorization` от
  клиента. Оба значения — в `LLM_RELAY_ENV_FILE` (`/opt/spectrek_fsp/secrets/llm_relay.env`). Проверено из
  песочницы: Sonnet через ретранслятор отвечает (3,5 с на коротком запросе, напрямую — 2,0 с), неверный токен — 404.
- В docker-compose `openrouter.env` и `llm_relay.env` — необязательные `env_file` (как `llm.env`): нет файла —
  цепочка без OpenRouter.

- Ретранслятор может стоять на своём сервере с самоподписанным сертификатом (IP в SAN): тогда задаётся
  `LLM_RELAY_CA_PEM_B64` (PEM в base64) или `LLM_RELAY_CA_FILE` — TLS ретранслятора проверяется только по этому
  сертификату (функция `_verify` в client.py), остальные провайдеры — по обычному хранилищу certifi.

## 4. Вторая оценка спорных ответов

Спорный ответ (`grader.doubts`, любое из условий):

- `near_threshold` — балл у порога зачёта: |x − 0,5| ≤ `LLM_GRADING_NEAR` (0,05);
- `level_mismatch` — уровень модели не согласован с баллом (weak при x ≥ 0,5 или strong при x < 0,5);
- `soft_signals` — мягкие признаки инъекции (обращение к проверяющему, «ответ сверен с эталоном», самооценка);
  жёсткие (`injection_signals`) в модель не уходят вовсе — сразу эксперту;
- `low_relevance` — высокий балл при слабой связи ответа с заданием.

Вторая оценка — независимый вызов другой модели (`grade_second`, Claude Fable 5.1): критерии и эталоны в обратном
порядке (против эффекта порядка), первая оценка не передаётся. Правило объединения консервативное:

- |x₁ − x₂| ≤ `LLM_GRADING_DISAGREE` (0,25) → среднее по каждому критерию, метод `llm2`;
- расхождение больше, вторая оценка не получена или не уложилась в бюджет → балла нет, ответ «на проверке»
  (`graders_disagree` / `second_opinion_failed`), решение за экспертом;
- вторая оценка вызывается, только если её модель отличается от модели первой (без цепочки поведение прежнее).

Обе оценки, модели и причины сомнения сохраняются в `grading` ответа (`scores`, `second`, `checks`, `model_label`) и
видны эксперту: «Две оценки: Claude Sonnet 5.5 0,50 и Claude Fable 5.1 0,75».

**В фоне (И27, `LLM_GRADING_SECOND_ASYNC=true`, по умолчанию).** Вторая оценка занимала ≈ 9,5 с, и кандидат ждал её
на ответе. Теперь ответ сразу получает балл первой оценки (`method: llm`, `second: {status: pending}`), вторая
модель вызывается в потоке после фиксации ответа (`assessment/second_opinion.py`): вызов — без блокировки сессии,
запись — под блокировкой (`SELECT … FOR UPDATE`), повторный запуск ничего не меняет. Результат дописывается в
`grading.second` с пометкой «пересмотрено второй моделью» и вердиктом `agree | disagree | manipulation | failed`:

- тест ещё идёт: согласие — среднее (`llm2`), иначе балл снимается и ответ уходит эксперту (как в синхронном режиме);
- тест уже завершён: **итог задним числом не меняется** — ответ помечается `disputed`, попадает в очередь эксперта
  («вторая — в фоне, после итога теста»), а оценка эксперта применяется с пересчётом итога и записью в журнал;
- кандидат видит в результате строку «Вторая модель пересматривает спорные ответы в фоне…» / «Пересмотрено второй
  моделью: n, передано эксперту: n» (`result.second_opinions`).

Тесты — `backend/tests/test_second_async.py` (не ждёт вторую модель; вердикты; в ходе теста — согласие и
расхождение; после итога — disputed → эксперт → пересчёт; повторный запуск; синхронный режим).

Доля вызовов: порог 0,05 выбран по первому проходу Sonnet на наборе оценщика (406 ответов, 357 дошли до модели):
0 → 14 %, 0,05 → 16,5 %, 0,1 → 18 %, 0,15 → 27 % вызовов. С 0,05 вторая оценка понадобилась 64 ответам из 406
(15,8 %; ориентир карточки 10–20 %): у порога — 60, мягкие признаки — 5, уровень не согласован — 4. Fable согласна в
59 случаях (|Δ| в среднем 0,07), расходится в 5 → эксперту (1,9 % честных ответов).

## 5. Персональные данные

Единственная точка выхода текста к внешним моделям — `llm/client.py` (OpenRouter через ретранслятор, Yandex AI Studio).
Данные платформы хранятся на сервере в Москве; в модель уходит только текст, из которого **локально** (на нашем
сервере, без сети) вырезаны персональные данные — `resume/pii.py`, функция `redact`, словари `resume/names.py`.
Тексты запросов в журналы не пишутся (только провайдер, модель, задержка, статус), у OpenRouter —
`provider.data_collection = deny`. Кадры камеры сервер не получают (анализ в браузере).

Четыре вызова модели: разбор потребности (`parse_need`), резюме (`resume`), оценка развёрнутого ответа (`grade`) и
вторая оценка спорных ответов (`grade_second`, тот же уже очищенный текст).

`row['ул.']` в коде — не адреса; «опыт от 3 лет», «7 лет 2 месяца» — не возраст. Слово, которое NER принял за имя без
признаков имени («Автотесты:» в начале строки), не режется — иначе пропадало из разбора.

**Проверка.** `tests/test_pii_llm_bodies.py` перехватывает тела запросов к модели во всех четырёх вызовах на 4
синтетических резюме (PDF через API), 2 вакансиях и ответе с ПДн (первая и вторая оценка) и проверяет, что там нет почты,
телефона, адреса, даты рождения, возраста, ФИО кириллицей и латиницей, а стек и город на месте. `tests/test_pii_candidate_view.py` —
кандидату не уходит сырой текст потребности (в нём бывают контакты рекрутёра): только название и требования.
`tools/realdata/pii_check.py` → `docs/realdata/pii_check.json`: на 50 реальных вакансиях — 0 новых вырезаний, разбор
правилами текста для модели не изменился (стек P/R 0,885 / 0,940, опыт 50/50, город 50/50); на всём банке заданий
(1,32 млн знаков условий и кода) — 0 новых плейсхолдеров, 6 ложных `[ник]` у декораторов кода убраны.

То же для файлов (`test_file_parse.py`, Ф5): вакансия из DOCX (контакты рекрутера) и резюме DOCX — в теле запроса к модели нет почты,
телефона и фамилии. Текст из файла идёт в модель тем же путём, что набранный (docs/FILE_PARSE.md).

**Остаточные риски (честно).** Вырезание — эвристики и локальный NER, а не гарантия:
- адрес без типа улицы и без подписи («Москва, Ленина 5-3» в середине текста) не распознаётся; метро без подписи остаётся;
- редкое имя латиницей не из словаря и без фамильного окончания вне шапки («Aru Bek, Python») может остаться;
- имя латиницей, совпадающее с обычным словом или технологией (Will, Ada, Ruby, Max), намеренно не режется — иначе пропадали бы
  слова из описания стека и задач; «Will Smith» в тексте вакансии остаётся;
- одиночное имя без контакта рядом («Ольга будет вашим наставником») в вакансии не режется — это сделано намеренно,
  чтобы не резать обычные слова;
- дата рождения без подписи ниже 10-й строки резюме, возраст без слов «год/лет» — остаются;
- название компании, вилка, адрес офиса без улицы в тексте вакансии уходят в модель (данные компании);
- в ответе на задание вырезание может заменить тестовые данные в коде («Иванов», «ул. Ленина») — цитата-доказательство
  тогда не совпадёт, критерий уйдёт на вторую оценку или эксперту;
- сырой текст потребности хранится в БД (`employer_needs.raw_text`, виден только своей компании).

**Для питча:** «До любой отправки в модель на нашем сервере в Москве локально вырезаются контакты, ссылки, ники,
адреса, даты рождения и возраст, документы и имена — кириллицей и латиницей (регулярные выражения, словари и локальная
модель NER); город остаётся для подбора. Тесты перехватывают каждый запрос к модели и проверяют, что ПДн там нет. Данные
компании (название, вилка) не маскируются; тексты запросов не логируются». Не говорить «ПДн в модель не попадают
никогда» — это эвристики с известными остаточными рисками (выше).

### Метод и границы слепоты

- [Нейтральный вход второго этапа](llm/extra_tags_judgement_blind_input_v2.json) — объединение расхождений
  **обеих** систем, перемешанное глобально; нет имени предложившей системы и признака «лишний / пропущенный».
  Для каждой пары единый вердикт, независимо от того, сколько систем предложило её.
  [Все 77 вердиктов](llm/extra_tags_judgement_verdicts_v2.json) зафиксированы до соединения с происхождением.
- **Граница слепоты:** текущий вход скрывает источники, но тот же исполнитель ранее видел результаты первой
  проверки правил. 57 ранее оценённых пар сохранили прежние решения, 20 дополнительных оценены по текстам;
  после просмотра происхождения и метрик решения не менялись. Это не исследование с новым исполнителем,
  который никогда не видел выдач; ограничение явно указано в [аудите](llm/extra_tags_judgement.json).
- Подтверждение требует прямого или однозначного смыслового указания, а не срабатывания широкого словарного
  триггера. Автоматические эквивалентности `REST → http`, `bash → linux`, `асинхронность → asyncio`,
  `ELK → siem-soc` не применяются. Конкретное описание методов и кодов ответов REST API допускается как
  смысловое подтверждение HTTP; этот пограничный случай специально отмечен для эксперта.
- Категория «обязательный» включает обычные задачи, требования и стек проекта без пометки «плюс»;
  **она не превращает альтернативу или описание окружения в персональный must-have**.
  Составные теги `html-css`, `ci-cd` допускают подтверждение явно указанного компонента;
  отсутствие второго компонента пояснено в вердикте. Приоритеты в P/R/F1 не оцениваются:
  как в исходном бенчмарке, обязательный и желательный стек объединяются в множество.
- Каждое подтверждение содержит дословную цитату и её смещения в замороженном тексте, а каждая запись —
  URL исходной вакансии и SHA-256 текста. Все цитаты и смещения автоматически проверены;
  исходный корпус, разметка и исторический бенчмарк **не изменены**.
  Политика и проверки доступны в [результате](llm/extra_tags_judgement.json).

## 9. Открытая модель на машине жюри (профиль `llm-local`)

**09.10.2026.** Для машины без GPU и без доступа к зарубежным API — своя открытая модель на CPU, без ключей.

### Одна команда

```bash
make llm-local      # = LLM_LOCAL_ENV_FILE=./infra/llm-local/llm-local.env docker compose --profile llm-local up -d --build
```

- Сервис `llm-local` — llama.cpp server (образ `ghcr.io/ggml-org/llama.cpp:server-b11515`, есть amd64 и arm64),
  OpenAI-совместимый API на `127.0.0.1:8143`. При первом старте сам скачивает с Hugging Face
  `unsloth/Qwen3.5-9B-GGUF:Q4_K_M` (5,7 ГБ, на сервере проверок — около 5 минут) в том `llm_models`; в репозитории
  и образе модели нет, повторный старт — без загрузки (около 10 с).
- api получает `LLM_CHAIN=local` из `infra/llm-local/llm-local.env`. Пока модель качается или если она не ответила,
  работает путь без LLM (автомат-выключатель после 3 ошибок подряд не ждёт её 60 с).
- Проверка: `curl -s localhost:8143/health` → `{"status":"ok"}`; `/api/meta` → `llm.chain` =
  `[{"provider": "local", "configured": true, "relay": false, "local": true}]`; на экране эксперта и в итоге теста —
  «Оценка: Qwen3.5 9B (локально)». Логи — `make llm-local-logs`, остановить — `make down`.
- Без профиля ничего не меняется: сервис не запускается, `LLM_CHAIN` в окружении api не задаётся (серверный `.env`
  не перекрывается), `LLM_LOCAL_BASE_URL` и `LLM_LOCAL_MODEL` без `local` в цепочке ни на что не влияют (тест).
- Постоянно (без `make`): `COMPOSE_PROFILES=llm-local` и `LLM_LOCAL_ENV_FILE=./infra/llm-local/llm-local.env` в `.env`.
- Машина 8 ГБ: `LLM_LOCAL_HF_REPO=unsloth/Qwen3.5-4B-GGUF:Q4_K_M`, `LLM_LOCAL_MODEL=qwen3.5-4b`,
  `LLM_LOCAL_MEM_LIMIT=4g` (файл 2,7 ГБ). Качество и скорость 4B **не замерялись** (на OpenRouter её нет, сервер
  проверок был занят), это вариант «лучше, чем ничего», а не проверенная рекомендация.

### Провайдер `local` (`llm/client.py`)

- Адрес — `LLM_LOCAL_BASE_URL` (по умолчанию в compose `http://llm-local:8080/v1`), модель — `LLM_LOCAL_MODEL`,
  ключ — `LLM_LOCAL_API_KEY` (необязателен; без него заголовка `Authorization` нет), тайм-аут попытки —
  `LLM_LOCAL_TIMEOUT_S` (CPU медленнее облака, поэтому свой).
- JSON-режим (`response_format: json_object` → грамматика llama.cpp, `LLM_LOCAL_JSON_MODE`), рассуждения выключены
  (`chat_template_kwargs.enable_thinking=false`, `LLM_LOCAL_NO_THINK`; блок `<think>…</think>`, если всё же пришёл,
  срезается), дополнительные поля тела — `LLM_LOCAL_EXTRA_BODY` (JSON).
- Подпись в интерфейсе — «Qwen3.5 9B (локально)»; в `/api/meta` адреса сервера модели нет.
- Ставится в цепочку как любой провайдер: `LLM_CHAIN=local` (только своя модель) или `LLM_CHAIN=openrouter,local`
  (облако, при его недоступности — своя модель). `LLM_MODEL_<FUNC>=off` — функция без модели, сразу путь без LLM.
- Вторая оценка спорного ответа в цепочке из одной `local` — та же Qwen: независимый вызов, критерии и эталоны в
  обратном порядке, первая оценка не передаётся. Независимость слабее, чем у пары Sonnet — Fable (раздел 4).
- Тесты — `backend/tests/test_llm_local.py` (подменённый транспорт httpx, без сети): тело запроса, JSON-режим,
  срез рассуждений, тайм-аут и бюджет, падение сервера → правила и автомат, облако → local, ПДн не уходят в модель,
  вторая оценка той же моделью, `off`, профиль compose и файл `llm-local.env`.

### Почему llama.cpp server, а не Ollama

Оба дают OpenAI-совместимый API на CPU. llama.cpp server выбран как более надёжный для «одной команды»: модель
скачивается самим сервером при первом старте (`--hf-repo`), а у Ollama нужен отдельный шаг `ollama pull` (или
своя точка входа); образ закреплён по номеру сборки; JSON-режим превращается в грамматику, поэтому невалидного JSON
почти нет; память управляется явно (`--load-mode none` — веса целиком в памяти процесса, `--cache-ram 512` — кэш
подсказок; по умолчанию у llama.cpp кэш до 8 ГБ, и на замере процесс вырос до 12,7 ГиБ); число потоков — по
`nproc` контейнера (`--threads -1` на 8 vCPU сервера проверок взял 192 потока по числу ядер хоста).

### Почему Qwen3.5-9B, а не Qwen2.5-7B

Обе — открытые веса, Q4_K_M помещаются в 16 ГБ. Сравнение — через OpenRouter теми же весами без квантования
(подробности — ниже), 09.10:

| | Qwen3.5-9B | Qwen2.5-7B-Instruct |
|---|---|---|
| Разбор 50 вакансий: стек P / R (модель + правила) | 0,785 / 0,957 и 0,793 / 0,964 (два прогона) | 0,796 / 0,940 |
| Разбор: «только модель» P / R | 0,805 / 0,709 | 0,782 / 0,487 |

| Оценщик: MAE к эталону A / B, r | 0,147 / 0,129; 0,65 / 0,67 | 0,209 / 0,202; 0,35 / 0,54 |
| Оценщик: эксперту из честных ответов | 3,1 % | 17,2 % (модель отмечает «попытку повлиять» на 33 честных ответах) |

Qwen2.5-7B втрое хуже извлекает стек сама и почти не различает манипуляцию и обычный ответ — для оценщика это

## 10. Быстрый разбор потребности и фон (И27)

Раньше `POST /api/employer/needs/parse` ждал модель: на стенде 4,5–10,7 с без промежуточного результата
(замер супервизора 08.10, отвечала yandexgpt). Теперь (`matching/fast_parse.py`, таблица `need_parse_jobs`,
миграция `fp01`):

1. **Сразу — словарь и правила** (`mode: fast`, по умолчанию): ответ за 10–40 мс, карточка заполнена, чип
   «разбор по словарю · уточняем моделью…», у ответа `parse_job: {id, status: pending}`.
2. **Модель — в фоне**, короткий запрос-дельта: модель получает текст (ПДн и признаки ст. 64 вырезаны) и сводку
   найденного словарём и возвращает только изменения — подтверждённые теги, добавленные теги с цитатами, теги на
   удаление, поправки грейда/формата/опыта — по строгой JSON-схеме (`response_format: json_schema`, перечисления
   тегов; если провайдер схему отклонил — повтор без схемы, попытка `schema_rejected`). Принимается только то, у
   чего цитата найдена в тексте. Лимиты: 4 фоновых разбора на пользователя, 4 одновременных вызова; задача старше
   120 с считается «модель не ответила».
3. **Интерфейс опрашивает** `GET /api/employer/needs/parse/{job_id}` (700 мс, до 60 с) и обновляет карточку сам, пока
   работодатель ничего не трогал. Если он уже подтвердил или поправил требования, изменения модели приходят
   предложениями «Принять / Отклонить / Принять все» — без молчаливой перезаписи.
4. **Кэш по нормализованному тексту** (NFC, переводы строк, пробелы по краям; ключ — sha256 текста + версия
   разбора, без ПДн; `PARSE_CACHE_TTL_S`, по умолчанию 3600 с): повтор того же текста — готовый результат модели
   за 3–7 мс («из кэша»).
5. **Происхождение у каждого требования**: «· словарь», «· Claude Sonnet 5.5, цитата найдена в тексте», «словарь ·
   подтверждено: Claude Sonnet 5.5»; над требованиями — «Claude Sonnet 5.5 добавила: … Подтвердила найденное
   словарём: …». Если модель не ответила — честное «разобрано словарём: модель не ответила»; без ключей —
   «разбор по словарю». Прежний синхронный полный разбор доступен как `mode: full`.

Замер 09.10 (песочница → OpenRouter напрямую, Claude Sonnet 5.5, через API приложения; 10 демо-потребностей:
4 из песочницы жюри, пример экрана, 5 из аудита подбора; 5 «жюрийных»: сленг, английский стек;
`tools/fastparse/bench.py`, результат — `tools/fastparse/bench_0910.json`):

| | До: ответ ждёт модель (`mode: full`) | После: первая карточка | После: модель в фоне | Повтор текста (кэш) |
|---|---|---|---|---|
| медиана | 2,20 с | 20 мс | 2,22 с | 3 мс |
| максимум | 3,02 с | 39 мс | 2,52 с | 7 мс |

Модель ответила на 15 из 15, повтор — из кэша 15 из 15. Итоговые теги (обязательные и желательные) у прежнего

### 10.2. «Свежий взгляд жюри» (И20): отрицания, вне справочника, один фрагмент — одно требование

- **Н1, отрицания.** Направление по слову под отрицанием не выбирается (`negated_directions`, `_DIR_NEG_BEFORE`):
  «фронтенд не нужен», «без фронтенда», «не нужен frontend» → не Frontend; «бэк», «бек» — Backend, «фаст апи»,
  «фастапи» — FastAPI. «Python или Java не нужен» — оба языка исключены, модель вернуть их не может (исключённые
  отрицанием теги передаются ей как «не добавлять» и отбрасываются после ответа). «Не обязателен, но плюс»
  (`_NEG_BUT_PLUS`, `DESIRED_CUES`) — желательно, а не исключение.
- **Н2, вне справочника.** Словарь знает «1С», Terraform, Excel, Power BI как «вне справочника» (`UNSUPPORTED_TECH`).
  В запросе-дельте — поле `unknown_required`: обязательные технологии, которых нет среди тегов, с цитатой. Принимается
  только термин с найденной в тексте цитатой, не тег справочника и не вариант уже найденного («1С:Предприятие» при
  «1С»). Такие термины показываются как «Вне справочника — проверить вручную», сохраняются в потребности
  (`Requirements.unknown_terms`, источник и модель у цитаты) и видны в версии подборки вместе с частичным
  соответствием категории («ближайшая категория — частичное соответствие (DevOps / SRE нет в каталоге)»). В
  ранжирование они не входят.
- **Н4, «REST» — одно требование.** Тег модели, чья цитата накрывает фрагмент, уже сопоставленный словарём с другим
  тегом, не добавляется («проектирование REST» → rest-api при REST → http; `_same_fragment`, счётчик
  `llm.same_fragment`), и «убрать http» при такой замене не предлагается. Запрос-дельта говорит модели то же, но с
  оговоркой: технологию, которую фрагмент подразумевает отдельно (DRF → rest-api), добавлять. Без оговорки модель
  стала пропускать REST API по «DRF» (замер 10.1).

### 10.3. Слияние словаря и модели; «офис в Москве» (09.10, вечер)

- **Опыт 0 — значение, а не «пусто».** Раньше `merged[key] = rules[key] or llm[key]`: «Опыт работы: не требуется» (0,
  vac-050) словарь находил, но слияние считало 0 пустым и брало число модели. Теперь значение словаря (в том числе 0)
  остаётся, несогласие модели — предложение «опыт: от N лет вместо 0» (принять / отклонить); модель заполняет опыт и
  формат только там, где словарь ничего не нашёл, и её 0 («можно без опыта») тоже принимается. Остальные поля (грейд,
  направление, формат, теги, вне справочника) не меняются.
- **«Удалённо или офис в Москве».** На стенде `c1c248e` разбор давал только «Удалённо», офис и Москва терялись
  (С2, выкладка 2). В integ (Ф2, `parse_conditions`) условия — объединение: «Удалённо или офис/гибрид (Москва)».
  Проверено на тексте С2 и на потребности песочницы жюри «…Офис в Москве или удалённо…» через весь путь: разбор
  словарём, фоновая модель (предложение модели сузить формат до одного не показывается), сохранение потребности,
  условия версии подборки (`conditions.applied`: три формата и город Москва). Добавлено «мск» как Москва («офис в мск
  или удалёнка»); «по МСК», «10–19 мск», «время МСК» — часовой пояс, не город.

### 10.4. Проход стенда супервизором, выкладка 3 (Я11, `fix/sup3`, 10.10)

Текст супервизора (С3-1…С3-3): «…Удалёнка не предусмотрена… опыт не требуется… обязательно: Python, Django,
PostgreSQL, Docker…» — на `601e2ba` давал формат «Удалённо или офис/гибрид», опыт 0 без цитаты и веса 0,85/0,53
(словарь 1,0/0,9/0,8/0,56, после модели — среднее со своим весом модели).

- **С3-1, отрицание формата после упоминания.** `_FMT_NEG_AFTER`: «не предусмотрена», «не практикуется», «не
  планируется», «удалённой работы нет», «удалённо не работаем», «отсутствует», not offered; между упоминанием и
  отрицанием — до двух служебных слов («работы», «формат», «у нас», «пока», «к сожалению»). «Только / исключительно /
  строго офис» (`_FMT_ONLY_BEFORE`) — остальные форматы исключены, даже если упомянуты без отрицания. «Офис 15» в
  адресе — не формат («офис 3 дня в неделю» — формат). `parse_conditions` возвращает `formats_excluded`; модель
  (полный разбор и фоновая дельта И27) не может предложить исключённый текстом формат.
- **С3-2, «опыт не требуется».** `_ZERO_EXP_RE`: «опыт не требуется / не обязателен / не нужен», «можно / рассмотрим /
  возьмём … без опыта», «без опыта — научим», no experience required → 0 с цитатой. Не ноль: «без опыта не
  рассматриваем», «не возьмём без опыта», «опыт с Kafka не требуется» (опыт конкретной технологии).
- **С3-3, веса.** Вес у тега словаря больше не усредняется с весом модели; навыку, который добавила модель, вес
  ставится тем же правилом по месту цитаты в тексте (`apply_weights`). Модель находит навыки и цитаты, вес не задаёт.
  Правило показано у «Настроить веса» (`weight_rule` в ответе разбора). По умолчанию — прежнее правило (по порядку

## 11. Режим «только российская модель»: замер

**09.10.2026.** Основная модель стенда — Claude Sonnet 5.5 через OpenRouter (остаётся). Для
заказчика, которому нужно «данные не уходят за рубеж», весь путь работает в режиме `LLM_CHAIN=yandex`: все четыре
LLM-функции идут только в Yandex AI Studio (YandexGPT 5.1, РФ), последний рубеж — те же правила. Режим без модели
вовсе (`LLM_DISABLED=true`) тоже работает: разбор — словарём, оценка открытых ответов — экспертом.

### Как включить

В `.env` сервера (ключ Yandex AI Studio — в `llm.env`: `LLM_PROVIDER=yandex_ai_studio`, `LLM_BASE_URL`, `LLM_API_KEY`,
`LLM_FOLDER_ID`, `LLM_MODEL`), затем пересоздать api (`docker compose up -d api`):

```
LLM_CHAIN=yandex
LLM_MODEL_PARSE_NEED=yandex=yandexgpt-5.1/latest
LLM_MODEL_RESUME=yandex=yandexgpt-5.1/latest
LLM_MODEL_GRADE=yandex=yandexgpt-5.1/latest
LLM_MODEL_GRADE_SECOND=yandex=yandexgpt-5.1/latest
# необязательно: JSON-схема ответа-дельты разбора и у Yandex (по умолчанию выключено, см. ниже)
# LLM_YANDEX_JSON_SCHEMA=true
```

Проверка: `/api/meta` → `llm.chain` = `[{"provider": "yandex", "configured": true, …}]`, у всех функций
`functions.*.models[0].label` = «YandexGPT 5.1»; чип разбора — «словарь + YandexGPT 5.1», оценка — «YandexGPT 5.1».
Ключ OpenRouter при этом может оставаться в окружении: провайдера нет в цепочке — запросов к нему нет (тест
`test_ru_llm.py::test_ru_only_routes_every_function_to_yandex`). Вторая оценка спорных ответов — та же YandexGPT
независимым вызовом (критерии и эталоны в обратном порядке, первая оценка не передаётся) — независимость слабее, чем у
пары Sonnet — Fable.

### Условия

- Одни и те же входы для всех; одна попытка на вход без перехода по цепочке и без автомата-выключателя; путь продукта
  целиком (вырезание ПДн и признаков ст. 64, проверка цитат, слияние с правилами); 4 запроса параллельно
  (`tools/llm/ru_llm_bench.py`). Вызовов на модель — около 610 (50 + 50 + 15 + 20 + 406 + 64 вторых).
- Sonnet — с машины замера в OpenRouter напрямую (на стенде — через ретранслятор, задержка там больше); вторая оценка в
  строке Sonnet — Claude Fable 5.1, как в продукте. YandexGPT — Yandex AI Studio, OpenAI-совместимый API, вторая
  оценка — та же модель (режим `LLM_CHAIN=yandex`).
- «Ответила» — продукт принял ответ; «формат» — ответ пришёл, но продукт его не принял (не JSON, не объект, нет баллов
  по всем критериям); «сеть» — тайм-аут, HTTP ≠ 200. Задержка p50 / p95 — по принятым ответам, только время модели.
- Цена — на 1000 вызовов функции: OpenRouter — фактическая (`usage.cost`), рубли — по курсу ЦБ РФ на 09.10.2026
  (85,42 ₽ за $); YandexGPT 5.1 — токены × 0,8 ₽ за 1000 входящих и исходящих (синхронный режим, с НДС, тариф
  [AI Studio](https://aistudio.yandex.ru/ru/docs/ai-studio/pricing) на 09.10.2026).
- Разметки не экспертные: вакансии — silver-разметка набора (модель + ручная сверка), резюме — автор набора (модель семейства
  Claude), оценщик — эталон gpt-oss-120b (модель). Согласие Sonnet с разметкой, сделанной моделью того же семейства,
  может быть завышено.

## 12. Сильнейшие модели по функциям: замер

**09–10.10.2026.** Мерили не только скорость, а всё, прежде всего качество ответов. Для каждой LLM-функции
продукта — одни и те же входы для всех моделей, путь продукта целиком (вырезание ПДн до вызова, проверка цитат, слияние с правилами, проверка вызывающего).
Модель стенда этим замером не меняется: выбор применяется отдельным решением (`LLM_MODEL_<ФУНКЦИЯ>`,
несколько моделей одного провайдера — через `|`, раздел 2).

### Что мерили

- **Разбор потребности** — 15 из 50 реальных вакансий (исправленная разметка) и 20 трудных синтетических потребностей
  (`docs/llm/needs_synth_hard.json`: отрицания «без удалёнки», «опыт не требуется», «X не нужен»; незнакомые стеки;
  сленг и английский): F1 стека, точность полей (специализация, грейд, формат, опыт, зарплата), отрицания, выдуманные
  навыки (теги вне разметки и допустимых), названы ли незнакомые стеки, цитаты-основания тегов модели; ещё 15
  «жюрийных» текстов — согласие с большинством других моделей.
- **Разбор резюме** — 20 синтетических резюме (`docs/llm/resume_synth.json`) и 6 резюме с вымышленными ПДн
  (`docs/llm/resume_pii_synth.json`): F1 навыков, лишние навыки, стаж ±0,5 года; ПДн — ушли ли в запрос (вырезание
  продукта до вызова) и «восстановила» ли модель их в ответе.
- **Оценка развёрнутых ответов** — 50 ответов набора панели (честные сильные/средние/слабые и атаки «поставь максимум»,
  служебные отметки): MAE и κw против эталона — среднего трёх сильнейших моделей двух семейств (Claude Opus 5.5 и
  Claude Fable 5.1 — Anthropic, GPT-6 Astra Pro — OpenAI) **без самой оцениваемой** (иначе «согласие с собой»); завышение и занижение (> 0,25), точное
  совпадение корзины, атаки, устойчивость (10 честных ответов ещё 2 раза — размах балла), обоснование (судья другой
  семьи: согласованность с баллом, опора цитат, качество русского текста 1–5). Разметка панели v2 сделана Fable 5.1 —
  риск той же семьи для моделей Anthropic.
- **Общее** — доля успешных ответов, пустые, невалидный JSON, срабатывание проверки вызывающего, доля тайм-аутов при
  бюджете стенда (разбор и резюме — 25 с, оценка — 50 с), p50/p95, фактическая цена (usage.cost OpenRouter) за 1000
  вызовов. Объяснения подборки, «почему», ранжирование — модель не вызывают (правила).

Итог на функцию — сводная оценка (качество главное, затем надёжность, задержка, цена) и выбор «сильнейшая в пределах
задержки»: лучшая по индексу качества среди моделей, у которых p95 не больше тайм-аута стенда и успешных ответов не
меньше 90 %; резерв — лучшая другой семьи; затем правила. Разница внутри пересекающихся интервалов — шум.

## 13. Доказательная оценка открытых ответов (флаг `GRADING_EVIDENCE`, по умолчанию выключен)

Цель — чтобы балл по каждому пункту рубрики опирался на фрагмент ответа, который видят кандидат и работодатель, а
решение о баллах принимал код по фиксированным правилам. Код — `backend/app/modules/assessment/evidence.py`,
выдача — `evidence_view.py`, замер — `tools/llm/evidence_bench.py`.

**Правило цитат.** Оценщик (промпт v3) по каждому пункту с баллом выше 0 приводит от одного до трёх дословных
фрагментов ответа. Программа сверяет их с текстом, ушедшим в модель (после вырезания ПДн): регистр, «ё», кавычки,
тире и пробелы приводятся к одному виду; фрагмент подтверждён, только если его слова идут в ответе подряд целыми
словами или куски через многоточие идут по порядку (каждый от двух слов). Нечёткого совпадения нет: пересказ,
пропущенное или добавленное слово (в том числе «не»), склейка без многоточия — не подтверждено; отрицание прямо
перед фрагментом в ответе («следует удалять» из «не следует удалять») — не подтверждено; меньше двух слов и повтор
условия задания (от 6 слов) — не доказательство. Неподтверждённые фрагменты отбрасываются и сохраняются с причиной.
**Пункт без подтверждённой цитаты не получает полный балл:** опускается на шаг (1 → 0,5, 0,5 → 0).

**Скептик.** Для оценки ≥ `GRADING_SKEPTIC_HIGH` (0,75) или спорной (причины сомнения `grader.doubts`) вместо
независимой второй оценки вызывается скептик (цепочка `grade_second`: Claude Fable 5.1 → Yandex, или
`GRADING_SKEPTIC_MODEL`). Он видит рубрику, эталоны, ответ между одноразовыми метками и баллы с подтверждёнными
цитатами и предлагает изменить отдельные пункты. Итог собирает код (`evidence.assemble`): снижение — не больше шага
за пункт; повышение — только с цитатой, которую подтвердил код, и тоже не больше шага; итог пересчитывается по весам;
сдвиг итога > 0,25 или пометка манипуляции — ответ уходит эксперту; скептик не ответил — спорный ответ уходит
эксперту, высокий без сомнений сохраняет первую оценку. Скептик работает в фоне тем же механизмом, что вторая оценка
(`LLM_GRADING_SECOND_ASYNC`): кандидат его не ждёт.

**Интерфейс.** «Доказательства: цитаты из ответа» с подписью «оценка модели» — на экране результата теста у кандидата
и в карточке кандидата у работодателя (кандидат может скрыть: «Цитаты из ответов теста» в настройках приватности).
Показываются «Пункт N», вес, балл, цитаты, число отброшенных, шаг вниз и поправки скептика; тексты пунктов рубрики,
эталоны и условия заданий закрыты. Блок замера — /validation, раздел «Цитаты оценщика».

**Исправление в пути по умолчанию (флаг выключен; находка независимого судьи 10.10).** Прежняя нечёткая сверка

ответе «данные следует удалять». Теперь цитата, у которой отрицание стоит не при тех же словах, что в ответе, не
подтверждается (в обе стороны), точное вхождение — целыми словами. На 935 сохранённых ответах 12 моделей на набор
