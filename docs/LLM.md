# LLM: цепочка моделей

Код: `backend/app/modules/llm/client.py` (цепочка, автомат-выключатель, ретранслятор), `assessment/grader.py`
(оценка открытых ответов, вторая оценка), `matching/need_parser.py` (разбор потребности), `resume/extract.py`
(резюме), `resume/pii.py` (вырезание ПДн). Тесты — `backend/tests/test_llm_chain.py` (подменённый транспорт httpx,
без сети). Прогоны — `tools/llm/`, результаты — `docs/llm/`.

## 1. Какая модель где и почему

| Функция | Цепочка (сервер, `LLM_CHAIN=openrouter,yandex`) | Тайм-аут | Рассуждения | Почему |
|---|---|---|---|---|
| `parse_need` — разбор вакансии | Claude Sonnet 5.5 → yandexgpt-5.1 → правила | 25 с | low | Sonnet: лучшая полнота стека среди ответивших на все 50 вакансий, 2,7 с; yandexgpt-5.1 — самая быстрая и надёжная запасная (раздел 6) |
| `resume` — разбор резюме (после вырезания ПДн) | Claude Sonnet 5.5 → yandexgpt-5.1 → словари | 25 с | low | та же задача извлечения, тот же выбор |
| `grade` — оценка открытого ответа | Claude Sonnet 5.5 → `LLM_GRADING_MODEL` (Yandex) → «на проверке» | 40 с | по умолчанию модели | на наборе оценщика: 0 из 116 атак проходят, порядок сильный > средний > слабый на 29 из 29 заданий, 2,7 с |
| `grade_second` — вторая оценка спорных | Claude Fable 5.1 → `LLM_GRADING_MODEL` → эксперт | 40 с | low | другая модель (независимая ошибка); вызывается для 16 % ответов (раздел 4) |

Без новых переменных поведение прежнее: один провайдер `LLM_*` (Yandex AI Studio), модель `LLM_MODEL`, оценка —
`LLM_GRADING_MODEL`, второй оценки нет (та же модель — не независимая).

Последний рубеж у каждой функции — путь без LLM: словарь стек-тегов и правила (разбор), статус «на проверке» и
эксперт (оценка). Интерфейс показывает, какая модель фактически ответила: «разбор: словарь + Claude Sonnet 5.5,
цитаты проверены», при переходе — имя запасной, если не ответил никто — «разбор по словарю: модель не ответила».
Цитата из вакансии подписана моделью, которая её нашла. В журнале проверки (экран эксперта) — обе оценки с именами
моделей.

## 2. Цепочка и автомат-выключатель

- Порядок — `LLM_CHAIN` (`openrouter,yandex`; провайдер без ключа пропускается). Переход к следующему: ошибка
  сети, тайм-аут, HTTP ≠ 200, ошибка в теле ответа, пустой ответ, невалидный JSON, ответ не прошёл проверку
  вызывающего (`validate`: например, у оценки нет балла по всем критериям). Причины — в `attempts` результата.
- Разбор JSON терпим к «поправкам»: если модель вывела объект, затем «Поправка: …» и второй объект — берётся
  последний целый объект; обрезанный ответ остаётся невалидным (переход дальше), внутренние объекты не берутся.
- Автомат-выключатель на пару «провайдер:модель»: `LLM_BREAKER_FAILURES` ошибок подряд (3) → пропуск
  `LLM_BREAKER_COOLDOWN_S` секунд (60), затем одна пробная попытка; успех закрывает автомат, ошибка — снова открывает.
  Недоступная модель второй оценки не выключает основную модель того же провайдера. `0` — автомат выключен.
- Модель, тайм-аут и усилие рассуждений — на функцию: `LLM_MODEL_<FUNC>` (`модель` — для первого провайдера цепочки
  или `openrouter=…,yandex=…`), `LLM_TIMEOUT_<FUNC>`, `LLM_REASONING_<FUNC>` (`low | medium | high | default`).
  У Sonnet 5.5 рассуждения не выключаются (HTTP 400), поэтому `low`: на длинной вакансии с рассуждениями по умолчанию
  827 из 1200 токенов ушли на рассуждения и JSON обрезался; с `low` — 0 токенов рассуждений, ответ вдвое дешевле.
- Общий бюджет оценки одного ответа — `LLM_GRADING_BUDGET_S` (50 с): первая и вторая оценка с переходами по цепочке
  укладываются в `proxy_read_timeout` nginx (60 с), ответ кандидата ждёт оценку синхронно. Не хватило времени на
  вторую оценку — ответ «на проверке» (повтор при завершении теста, затем эксперт).
- `/api/meta` → `llm`: `chain` (провайдеры, настроен ли, через ретранслятор ли), `functions` (модели по порядку,
  тайм-аут), `breaker` (открытые автоматы), `last` (кто ответил последним по функции и был ли переход). Ключей,
  адреса ретранслятора и каталога Yandex Cloud там нет; прежние поля `configured`, `provider`, `model` сохранены.

## 3. OpenRouter и ретранслятор

- Ключ — `OPENROUTER_API_KEY` (файл `OPENROUTER_ENV_FILE`, на сервере `/opt/spectrek_fsp/secrets/openrouter.env`).
  Заголовки атрибуции нейтральные: `HTTP-Referer: https://localhost`, `X-Title: llm-client` — без названия
  продукта и домена (тест). В теле — `provider.data_collection = deny` (провайдеры, хранящие запросы для обучения,
  исключаются).
- Ретранслятор: OpenRouter определяет страну исходного запроса, с сервера в РФ — 403. Если задан `LLM_RELAY_URL`,
  клиент ходит на него (базовый адрес OpenAI-совместимого API уже с `/api/v1`, клиент добавляет
  `/chat/completions`) и добавляет `X-Relay-Token: LLM_RELAY_TOKEN`; ключ OpenRouter — в `Authorization` от
  клиента. Оба значения — в `LLM_RELAY_ENV_FILE` (`/opt/spectrek_fsp/secrets/llm_relay.env`). Проверено из
  песочницы: Sonnet через ретранслятор отвечает (3,5 с на коротком запросе, напрямую — 2,0 с), неверный токен — 404.
- В docker-compose `openrouter.env` и `llm_relay.env` — необязательные `env_file` (как `llm.env`): нет файла —
  цепочка без OpenRouter.

- Ретранслятор может стоять на своём сервере с самоподписанным сертификатом (IP в SAN): тогда задаётся
  `LLM_RELAY_CA_PEM_B64` (PEM в base64) или `LLM_RELAY_CA_FILE` — TLS ретранслятора проверяется только по этому
  сертификату (функция `_verify` в client.py), остальные провайдеры — по обычному хранилищу certifi.

## 4. Вторая оценка спорных ответов

Спорный ответ (`grader.doubts`, любое из условий):

- `near_threshold` — балл у порога зачёта: |x − 0,5| ≤ `LLM_GRADING_NEAR` (0,05);
- `level_mismatch` — уровень модели не согласован с баллом (weak при x ≥ 0,5 или strong при x < 0,5);
- `soft_signals` — мягкие признаки инъекции (обращение к проверяющему, «ответ сверен с эталоном», самооценка);
  жёсткие (`injection_signals`) в модель не уходят вовсе — сразу эксперту;
- `low_relevance` — высокий балл при слабой связи ответа с заданием.

Вторая оценка — независимый вызов другой модели (`grade_second`, Claude Fable 5.1): критерии и эталоны в обратном
порядке (против эффекта порядка), первая оценка не передаётся. Правило объединения консервативное:

- |x₁ − x₂| ≤ `LLM_GRADING_DISAGREE` (0,25) → среднее по каждому критерию, метод `llm2`;
- расхождение больше, вторая оценка не получена или не уложилась в бюджет → балла нет, ответ «на проверке»
  (`graders_disagree` / `second_opinion_failed`), решение за экспертом;
- вторая оценка вызывается, только если её модель отличается от модели первой (без цепочки поведение прежнее).

Обе оценки, модели и причины сомнения сохраняются в `grading` ответа (`scores`, `second`, `checks`, `model_label`) и
видны эксперту: «Две оценки: Claude Sonnet 5.5 0,50 и Claude Fable 5.1 0,75».

**В фоне (И27, `LLM_GRADING_SECOND_ASYNC=true`, по умолчанию).** Вторая оценка занимала ≈ 9,5 с, и кандидат ждал её
на ответе. Теперь ответ сразу получает балл первой оценки (`method: llm`, `second: {status: pending}`), вторая
модель вызывается в потоке после фиксации ответа (`assessment/second_opinion.py`): вызов — без блокировки сессии,
запись — под блокировкой (`SELECT … FOR UPDATE`), повторный запуск ничего не меняет. Результат дописывается в
`grading.second` с пометкой «пересмотрено второй моделью» и вердиктом `agree | disagree | manipulation | failed`:

- тест ещё идёт: согласие — среднее (`llm2`), иначе балл снимается и ответ уходит эксперту (как в синхронном режиме);
- тест уже завершён: **итог задним числом не меняется** — ответ помечается `disputed`, попадает в очередь эксперта
  («вторая — в фоне, после итога теста»), а оценка эксперта применяется с пересчётом итога и записью в журнал;
- кандидат видит в результате строку «Вторая модель пересматривает спорные ответы в фоне…» / «Пересмотрено второй
  моделью: n, передано эксперту: n» (`result.second_opinions`).

Тесты — `backend/tests/test_second_async.py` (не ждёт вторую модель; вердикты; в ходе теста — согласие и
расхождение; после итога — disputed → эксперт → пересчёт; повторный запуск; синхронный режим).

Доля вызовов: порог 0,05 выбран по первому проходу Sonnet на наборе оценщика (406 ответов, 357 дошли до модели):
0 → 14 %, 0,05 → 16,5 %, 0,1 → 18 %, 0,15 → 27 % вызовов. С 0,05 вторая оценка понадобилась 64 ответам из 406
(15,8 %; ориентир карточки 10–20 %): у порога — 60, мягкие признаки — 5, уровень не согласован — 4. Fable согласна в
59 случаях (|Δ| в среднем 0,07), расходится в 5 → эксперту (1,9 % честных ответов).

## 5. Персональные данные

В модель уходит только обезличенный текст (`resume/pii.py`, `redact`):

- резюме и открытый ответ — ФИО (NER), email, телефон, ссылки на профили и мессенджеры (GitHub, GitLab, GitFlic,
  LinkedIn, hh.ru, Хабр, Telegram и `@ник`, VK, LeetCode, Stack Overflow, Kaggle, Codeforces, X/Twitter,
  Behance, Dribbble);
- вакансия — плюс контактные лица после подсказок «Рекрутер — Пётр Сидоров», «HR: Ольга», «Контактное лицо: …»
  (на 50 реальных вакансиях — 0 ложных срабатываний; NER по всему тексту давал 12, например «Гибрид»), а также
  признаки ст. 64 ТК РФ (маскируются до вызова).

Тесты (`test_no_pii_in_*`) перехватывают тела запросов к модели при разборе вакансии, загрузке резюме (PDF через
API) и оценке ответа и проверяют, что ни ФИО, ни email, ни телефон, ни ссылки на профили туда не попали.

## 7. Как воспроизвести

```bash
# ключи — только в окружении процесса
python tools/llm/bench_needs.py --models openrouter=anthropic/claude-sonnet-5.5,yandex=yandexgpt-5.1/latest \
    --out docs/llm/needs_bench.json
# набор оценщика: во временной копии feat/integrity
python -m app.modules.validation.grader_check build --cond v2 --out /tmp/g/v2_1.jsonl
python tools/llm/chain_runner.py --requests /tmp/g/v2_1.jsonl --out /tmp/g/v2_1_out.jsonl \
    --model openrouter=anthropic/claude-sonnet-5.5 --func grade
python -m app.modules.validation.grader_check second --req /tmp/g/v2_1.jsonl --res /tmp/g/v2_1_out.jsonl \
    --out /tmp/g/v2_2.jsonl
python tools/llm/chain_runner.py --requests /tmp/g/v2_2.jsonl --out /tmp/g/v2_2_out.jsonl \
    --model openrouter=anthropic/claude-fable-5.1 --func grade_second --max-tokens 3000
python -m app.modules.validation.grader_check report --dir /tmp/g
```

### Один новый прогон, не восстановление старого

В историческом [бенчмарке](llm/needs_bench.json) итоговый Sonnet дал TP/FP/FN = 297/59/5,
но стеки по вакансиям не были сохранены. После WIP-проверки правил штаб разрешил **один новый отдельный прогон**
и сохранение полного стека. Исторические 59 лишних и 5 пропущенных пар не восстановлены:
новые решения и метрики **не приписываются старому прогону**; это явно отмечено в
[истории аудита](llm/extra_tags_judgement.json).

Новый прогон: `anthropic/claude-sonnet-5.5`, reasoning **low**, **max_tokens 2500**, тайм-аут 25 с,

### Метод и границы слепоты

- [Нейтральный вход второго этапа](llm/extra_tags_judgement_blind_input_v2.json) — объединение расхождений
  **обеих** систем, перемешанное глобально; нет имени предложившей системы и признака «лишний / пропущенный».
  Для каждой пары единый вердикт, независимо от того, сколько систем предложило её.
  [Все 77 вердиктов](llm/extra_tags_judgement_verdicts_v2.json) зафиксированы до соединения с происхождением.
- **Граница слепоты:** текущий вход скрывает источники, но тот же исполнитель ранее видел результаты первой
  проверки правил. 57 ранее оценённых пар сохранили прежние решения, 20 дополнительных оценены по текстам;
  после просмотра происхождения и метрик решения не менялись. Это не исследование с новым исполнителем,
  который никогда не видел выдач; ограничение явно указано в [аудите](llm/extra_tags_judgement.json).
- Подтверждение требует прямого или однозначного смыслового указания, а не срабатывания широкого словарного
  триггера. Автоматические эквивалентности `REST → http`, `bash → linux`, `асинхронность → asyncio`,
  `ELK → siem-soc` не применяются. Конкретное описание методов и кодов ответов REST API допускается как
  смысловое подтверждение HTTP; этот пограничный случай специально отмечен для эксперта.
- Категория «обязательный» включает обычные задачи, требования и стек проекта без пометки «плюс»;
  **она не превращает альтернативу или описание окружения в персональный must-have**.
  Составные теги `html-css`, `ci-cd` допускают подтверждение явно указанного компонента;
  отсутствие второго компонента пояснено в вердикте. Приоритеты в P/R/F1 не оцениваются:
  как в исходном бенчмарке, обязательный и желательный стек объединяются в множество.
- Каждое подтверждение содержит дословную цитату и её смещения в замороженном тексте, а каждая запись —
  URL исходной вакансии и SHA-256 текста. Все цитаты и смещения автоматически проверены;
  исходный корпус, разметка и исторический бенчмарк **не изменены**.
  Политика и проверки доступны в [результате](llm/extra_tags_judgement.json).

## 9. Быстрый разбор потребности и фон (И27)

Раньше `POST /api/employer/needs/parse` ждал модель: на стенде 4,5–10,7 с без промежуточного результата
(замер супервизора 08.10, отвечала yandexgpt). Теперь (`matching/fast_parse.py`, таблица `need_parse_jobs`,
миграция `fp01`):

1. **Сразу — словарь и правила** (`mode: fast`, по умолчанию): ответ за 10–40 мс, карточка заполнена, чип
   «разбор по словарю · уточняем моделью…», у ответа `parse_job: {id, status: pending}`.
2. **Модель — в фоне**, короткий запрос-дельта: модель получает текст (ПДн и признаки ст. 64 вырезаны) и сводку
   найденного словарём и возвращает только изменения — подтверждённые теги, добавленные теги с цитатами, теги на
   удаление, поправки грейда/формата/опыта — по строгой JSON-схеме (`response_format: json_schema`, перечисления
   тегов; если провайдер схему отклонил — повтор без схемы, попытка `schema_rejected`). Принимается только то, у
   чего цитата найдена в тексте. Лимиты: 4 фоновых разбора на пользователя, 4 одновременных вызова; задача старше
   120 с считается «модель не ответила».
3. **Интерфейс опрашивает** `GET /api/employer/needs/parse/{job_id}` (700 мс, до 60 с) и обновляет карточку сам, пока
   работодатель ничего не трогал. Если он уже подтвердил или поправил требования, изменения модели приходят
   предложениями «Принять / Отклонить / Принять все» — без молчаливой перезаписи.
4. **Кэш по нормализованному тексту** (NFC, переводы строк, пробелы по краям; ключ — sha256 текста + версия
   разбора, без ПДн; `PARSE_CACHE_TTL_S`, по умолчанию 3600 с): повтор того же текста — готовый результат модели
   за 3–7 мс («из кэша»).
5. **Происхождение у каждого требования**: «· словарь», «· Claude Sonnet 5.5, цитата найдена в тексте», «словарь ·
   подтверждено: Claude Sonnet 5.5»; над требованиями — «Claude Sonnet 5.5 добавила: … Подтвердила найденное
   словарём: …». Если модель не ответила — честное «разобрано словарём: модель не ответила»; без ключей —
   «разбор по словарю». Прежний синхронный полный разбор доступен как `mode: full`.

### 9.2. «Свежий взгляд жюри» (И20): отрицания, вне справочника, один фрагмент — одно требование

- **Н1, отрицания.** Направление по слову под отрицанием не выбирается (`negated_directions`, `_DIR_NEG_BEFORE`):
  «фронтенд не нужен», «без фронтенда», «не нужен frontend» → не Frontend; «бэк», «бек» — Backend, «фаст апи»,
  «фастапи» — FastAPI. «Python или Java не нужен» — оба языка исключены, модель вернуть их не может (исключённые
  отрицанием теги передаются ей как «не добавлять» и отбрасываются после ответа). «Не обязателен, но плюс»
  (`_NEG_BUT_PLUS`, `DESIRED_CUES`) — желательно, а не исключение.
- **Н2, вне справочника.** Словарь знает «1С», Terraform, Excel, Power BI как «вне справочника» (`UNSUPPORTED_TECH`).
  В запросе-дельте — поле `unknown_required`: обязательные технологии, которых нет среди тегов, с цитатой. Принимается
  только термин с найденной в тексте цитатой, не тег справочника и не вариант уже найденного («1С:Предприятие» при
  «1С»). Такие термины показываются как «Вне справочника — проверить вручную», сохраняются в потребности
  (`Requirements.unknown_terms`, источник и модель у цитаты) и видны в версии подборки вместе с частичным
  соответствием категории («ближайшая категория — частичное соответствие (DevOps / SRE нет в каталоге)»). В
  ранжирование они не входят.
- **Н4, «REST» — одно требование.** Тег модели, чья цитата накрывает фрагмент, уже сопоставленный словарём с другим
  тегом, не добавляется («проектирование REST» → rest-api при REST → http; `_same_fragment`, счётчик
  `llm.same_fragment`), и «убрать http» при такой замене не предлагается. Запрос-дельта говорит модели то же, но с
  оговоркой: технологию, которую фрагмент подразумевает отдельно (DRF → rest-api), добавлять. Без оговорки модель
  стала пропускать REST API по «DRF» (замер 9.1).

### 9.3. Слияние словаря и модели; «офис в Москве» (09.10, вечер)

- **Опыт 0 — значение, а не «пусто».** Раньше `merged[key] = rules[key] or llm[key]`: «Опыт работы: не требуется» (0,
  vac-050) словарь находил, но слияние считало 0 пустым и брало число модели. Теперь значение словаря (в том числе 0)
  остаётся, несогласие модели — предложение «опыт: от N лет вместо 0» (принять / отклонить); модель заполняет опыт и
  формат только там, где словарь ничего не нашёл, и её 0 («можно без опыта») тоже принимается. Остальные поля (грейд,
  направление, формат, теги, вне справочника) не меняются.
- **«Удалённо или офис в Москве».** На стенде `c1c248e` разбор давал только «Удалённо», офис и Москва терялись

  словарём, фоновая модель (предложение модели сузить формат до одного не показывается), сохранение потребности,
  условия версии подборки (`conditions.applied`: три формата и город Москва). Добавлено «мск» как Москва («офис в мск
  или удалёнка»); «по МСК», «10–19 мск», «время МСК» — часовой пояс, не город.
