# Как строится порядок подборки (match-v2)

Код — `backend/app/modules/matching/ranking.py` (`build_selection` → `order_bundles`) и `ltr.py`; включается флагом
`MATCH_V2=1` (без флага — прежний match-v1.3). Один и тот же код строит подборку по потребности, «свой набор» жюри
(`bench_upload.py`) и бенчмарк (`tools/realdata/bench2.py`).

## 1. Кто попадает в подборку

1. **Категория — только по тесту.** Потребность разбирается в направление и грейд (`need_parser.py`); в подборку идут
   кандидаты, чей грейд в этом направлении подтверждён тестом (в том числе «предварительно» у порога). Заявленный в
   анкете грейд ни фильтром, ни баллом не служит (правило экспертов 20.10, тесты `test_a5_expert_rule.py`).
2. **Добор ступенью выше**, если подтверждённых в точной категории меньше 30 (`grade_above.py`): первые два места —
   лучшие точного уровня, дальше точный уровень раньше.
3. **Ярус «грейд не подтверждён»** — после всех подтверждённых, по направлению из опроса; ему не присваивается
   заявленный грейд.
4. **Условия работодателя** (формат, город, вилка) — фильтр; самоописание в балл не входит.

## 2. Стек вакансии — фильтр каскадом

Сначала кандидаты, у которых **все** обязательные навыки потребности заявлены или подтверждены тестом/заданием, затем —
у кого их не меньше 2/3, 1/2, 1/3, затем остальные (`ltr.stack_filter`, `ltr.THRESHOLDS`). Никого не прячем: в резюме
часть настоящих навыков не указана, и порог «все обязательные» терял релевантных. Ступень фильтра баллов не даёт —
внутри ступени место решает только балл.

## 3. Балл (место внутри ступени) — только проверенное

Линейная модель «из 100», вклад каждого признака виден HR (`ltr.contributions`, «Как считается» в `MatchExplain`):

| Признак | Откуда | Смысл |
|---|---|---|
| сила результата теста | тест | σ(1,7·(θ − порог запрошенного грейда)) |
| уверенность, что уровень не ниже запрошенного | тест | 1 − Φ((порог − θ)/SE) — учитывает точность теста |
| результат в полосе запрошенного грейда | тест | 1 − σ(1,7·(θ − порог следующего грейда)); «сильнее запроса» уменьшает его |
| достижения ФСП | реестр, официальные протоколы | фиксированная доля балла (требование ТЗ); протокол весит больше заявки; нет истории ФСП — штраф 0 |
| короткие задания работодателя | задания | 2 · доля верных − 1; заданий нет — 0 (проваленное опускает) |
| навыки, подтверждённые тестом; «проверка не подтвердила»; «предварительно» | тест, задания | доли и знаки — из обучения |

Доли признаков — `backend/app/modules/matching/ltr_weights.json` (`python3 -c "import json;
print(json.load(open('backend/app/modules/matching/ltr_weights.json'))['weights'])"`), обучение — только на мирах
разработки бенчмарка (`tools/realdata/ltr_train.py`), отложенные миры для этого не используются. Знак у «результат
в полосе запрошенного грейда» — из данных: кандидат, чей тест выше порога следующего грейда, идёт после тех, кто
точно в запрошенном грейде (работодатель просил этот грейд), и объяснение это говорит прямо.

## 4. Ключ сортировки

ярус статуса грейда (подтверждён/предварительно → не подтверждён) → ступень фильтра стека → [добор выше: точный
уровень раньше] → балл → рейтинг → публичный номер (детерминированно).

## 5. Дозапрос — вторая ступень

Работодатель отправляет первым кандидатам короткие задания по стеку потребности (`POST /api/employer/assignments`,
`mode=probe`); ответы становятся фактами T1 по навыкам и входят в балл при следующем пересчёте подборки (сквозная
проверка — `backend/tests/test_a5_dozapros_e2e.py`).

## 6. «Почему A выше B»

`compare.why_pairs`: разница баллов раскладывается по вкладам признаков модели без остатка (только подтверждённое:
тест, задания — T1, ФСП — T2).

Проверка порядка на отложенных мирах — `docs/realdata/bench_holdout2_PROTOCOL.md`.
