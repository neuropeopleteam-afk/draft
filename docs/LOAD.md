# Нагрузка 100–200 пользователей по сценариям жюри и развёртывание с нуля (09–10.10.2026)

Продолжение [docs/LOAD_TEST.md](LOAD_TEST.md) (05.10: 50 пользователей на временных учётках). Здесь — сценарии эксперта
жюри (вход в один клик, своя песочница), 100 и 200 одновременных пользователей, всплеск «пять экспертов входят разом»,
тяжёлые действия (открытый ответ с оценкой, резюме, «Красная кнопка»), контроль памяти api и проверка «чистый клон →
работает» строго по README. Все данные — **модельные (модель, не люди)**: 500 синтетических кандидатов демо-набора и
персоны песочницы жюри; настоящих людей нет.

## 2. Условия

- **Сервер стенда**: 4 vCPU, 7,9 ГБ ОЗУ (свободно ~5,5 ГБ), диск — 18–19 ГБ свободно. Стек `docker-compose.yml`:
  api — FastAPI, **2 воркера uvicorn** в одном контейнере, лимит 1536 МиБ; db — PostgreSQL 16, 320 МиБ; web — nginx
  со сборкой React, 32 МиБ; keycloak (ФСП ID, демо) — 576 МиБ. Лимиты CPU у контейнеров стенда не заданы.
- **nginx хоста** перед стеком: `limit_req` 10 запросов/с с адреса, для страниц (`location /`) очередь 300, личная
  ссылка `/x/` — очередь 20, `/api/` — без лимита. Генератор нагрузки — **один адрес**, поэтому ответ 429 на страницы
  при 200 пользователях — защита nginx от одного адреса, а не отказ приложения; в сводке такие ответы считаются отдельно.
- **Вход**: cookie личной ссылки эксперта `/x/<токен>` для страниц (без базовой авторизации), API — токен демо-входа
  жюри. Все виртуальные пользователи — в **одной отдельной песочнице жюри** (создаёт `run_load.py prepare`, удаляет
  `cleanup` или администратор стенда); общий демо-набор и песочницы экспертов не затрагиваются.
- **LLM**: на стенде включена цепочка (основная модель через OpenRouter с ретранслятором, запасная — YandexGPT;
  `/api/meta` → `llm.chain`). Сценарии по возможности без LLM; где без модели нельзя — потолок за прогон и подпись
  в имени запроса (раздел 3). Локальный стенд и временная копия — LLM выкл. (правила).
- **Лимиты продукта**, которые видны в нагрузке как ожидаемые ответы, а не ошибки: 30 стартов теста в сутки на
  демо-учётку; одна активная сессия теста на учётку и направление; повторное приглашение кандидату — 409
  `invitation_cooldown`; «Красная кнопка» — 12 атак в минуту на учётку (429); резюме — 5 в час на учётку; новых
  песочниц — 40 в час с адреса и 120 всего, хранится не больше 60 (старые вытесняются).
- **Связь песочницы генератора со стендом теряет часть запросов** (известная особенность рабочего места): ошибки
  соединения (код 0) сверяются с журналом nginx стенда — дошёл ли запрос до сервера.

## 3. Сценарии

Файлы: `tools/loadtest/jury_load.py` (Locust), `tools/loadtest/flows.py` (ответы на задания, тексты потребностей,
резюме, тела атак — без сети), `tools/loadtest/run_load.py` (подготовка, прогон, сводка, удаление). Тест сценариев —
`backend/tests/test_loadtest_jury.py` (проходит по API тестового клиента: экспресс-тест до итога, потребность →
подборка → сравнение → приглашение, резюме DOCX, «Красная кнопка»).

| Роль | Число | Что делает | LLM |
|---|---|---|---|

Паузы — как у человека: 1–4 с между действиями, 5–15 с между страницами `/validation`. Разгон — 2 пользователя в
секунду. В CSV у запросов фиксированные имена (по действию), личный токен и id песочницы в журналы не попадают.

## 4. Как воспроизвести

```bash
python3 -m venv /tmp/lt && /tmp/lt/bin/pip install locust==2.46.0      # отдельное окружение, не в .venv проекта
export LOCUST=/tmp/lt/bin/locust LT_STATE=/tmp/lt_jury_state.json
H=https://fsp.neuropeople.pro            # или локальный стенд http://127.0.0.1:8141
python3 tools/loadtest/run_load.py preflight --host $H --xlink-file <файл с JURY_LINK_1=…>   # всё ли готово
python3 tools/loadtest/run_load.py prepare --host $H                    # отдельная песочница жюри для прогона
python3 tools/loadtest/run_load.py run --host $H -u 100 -r 2 -t 11m --tag stand_100 \
    --xlink-file <файл с JURY_LINK_1=…> --server-stats --burst-at 300 --burst-n 5
python3 tools/loadtest/run_load.py run --host $H -u 200 -r 2 -t 12m --tag stand_200 \
    --xlink-file <файл с JURY_LINK_1=…> --server-stats --burst-at 300 --burst-n 5
python3 tools/loadtest/run_load.py nginx --tag stand_100                # сколько запросов дошло до nginx, коды
python3 tools/loadtest/run_load.py summary --tag stand_100              # p50/p95/p99 по операциям, ошибки, ресурсы
python3 tools/loadtest/run_load.py cleanup --host $H                    # удалить песочницы прогона и всплеска
```

Одной командой — `tools/loadtest/stand_night.sh`: `preflight` → `prepare` → 100 пользователей (11 мин, всплеск на
300-й секунде) → пауза 3 мин → 200 пользователей (12 мин) → по каждому прогону сверка с журналом nginx и сводка
(`docs/loadtest/<tag>_summary.md`) → `cleanup`. Песочницы прогона удаляются и при ошибке или остановке; второй прогон
не начинается, если `/api/health` не 200 или доля ошибок первого больше 10 % (`MAX_FAIL`).

```bash
export X=<файл с JURY_LINK_1=…> KPY=<SSH-обёртка сервера стенда> LOCUST=/tmp/lt/bin/locust
setsid nohup tools/loadtest/stand_night.sh > /tmp/stand_night.log 2>&1 < /dev/null &
# локально: H=http://127.0.0.1:8141 WEB=<адрес сборки> RUNS="dbg:12:2m" LT_OUT=/tmp/lt_out tools/loadtest/stand_night.sh
```

`run_load.py preflight` перед прогоном проверяет: Locust, `/api/health`, LLM по `/api/meta` (вкл./выкл., цепочка),
вход по личной ссылке (302 и cookie `fsp_x`), на сервере (только чтение) — load average, память, диск, контейнеры
стека, время запуска api, значение `JURY_SPARE_SANDBOXES` у api и не идёт ли выкладка или сборка; при ошибке — код 1
и «прогон не начинать». `run_load.py nginx --tag …` после прогона считает строки журнала nginx хоста с User-Agent
прогона (`spectrek-load/<tag>`, всплеск — `…-burst`): коды ответа и неуспешные по началу пути — только счётчики,
без адресов и токенов. `LT_OUT=/tmp/…` — каталог результатов отладочных прогонов вне репозитория. Для шагов на
сервере `run_load.py` запускается интерпретатором, в котором есть `paramiko` (его использует SSH-обёртка).

`--server-stats` (только чтение, через SSH-обёртку рабочего места): `docker stats` каждые ~10 с, `loadavg`, у api —
cgroup `memory.events` до и после прогона и `memory.peak` (OOM ловится как рост `oom_kill`). Результаты —
`docs/loadtest/<tag>_*.csv`, `<tag>_burst.json`, `<tag>_server.txt`. Время прогона 10 минут — после разгона
(100 пользователей при 2/с — 50 с). Только всплеск, без фоновой нагрузки: `run_load.py burst --host $H -n 5 --tag …`.

## 5. Всплеск «пять экспертов входят разом»

Вход эксперта «в один клик» со своей песочницей: если есть **запасная** песочница (готовится заранее в фоне), вход
мгновенный; если нет — песочница создаётся во время запроса (учётки персон, кандидаты, потребности, подборка —
секунды CPU). Создание идёт **по очереди** между воркерами (advisory lock PostgreSQL), а запас по умолчанию —
одна песочница (`JURY_SPARE_SANDBOXES=1`). Пять входов разом: первый забирает запасную, остальные четыре ждут друг
друга, и всё это время воркер занят — у остальных пользователей растут задержки.

Локальный замер (SQLite, 1 воркер, 2 общих ядра; на SQLite блокировки нет, создания идут параллельно и делят CPU):

| Запас песочниц | Вход 5 экспертов разом | Первый экран | Ошибки |
|---|---|---|---|
| 1 (по умолчанию) | 0,1 с; остальные 4 — 108–114 с | до 114 с | 1 × 500 «database is locked» — только SQLite, на PostgreSQL этого нет |
| 5 (`JURY_SPARE_SANDBOXES=5`) | **0,1–1,0 с у всех пяти** | до 1,06 с | 0 |

Запас из 5 песочниц набирается в фоне по одной (каждое открытие главной запускает пополнение); локально — около
2 минут. Места в БД — ≈ 0,1 МБ на песочницу, лимит хранения 60 не меняется. На временной копии с лимитом 1,5 CPU
одиночное создание песочницы при входе (без запасной) — 19–32 с; на стенде без лимита CPU — замер в разделе 6.

**Рекомендация на дни оценки**: `JURY_SPARE_SANDBOXES=5` в `.env` стенда и пересоздание api
(`docker compose up -d api`) — решение и выкладка за администратором стенда.

## 6. Стенд: 100 и 200 пользователей

### 6.1. 100 пользователей, 10.10, 13:05–13:17 МСК (до исправления)

Стенд — версия волны 4, `JURY_SPARE_SANDBOXES=5`; 100 виртуальных пользователей (модель, не люди) в отдельной
песочнице, разгон 2 в секунду, 11 минут, всплеск 5 холодных входов на 300-й секунде. Полные таблицы —
[docs/loadtest/stand_100_summary.md](loadtest/stand_100_summary.md), сырые данные — `docs/loadtest/stand_100_*`.

| Показатель | Значение |
|---|---|
| Запросов / в секунду | 8223 / 12,0 |
| Ошибок | **42 (0,51 %)**: 36 × 500, 7 × 504 (`/validation/report`), 1 × 504 (`leak_bank`); 429 «Красной кнопки» — правило продукта, не ошибка |
| Время ответа, всего | p50 0,93 с, p95 10 с, p99 31 с, макс. 64,9 с |
| Самые медленные (p50) | вакансии кандидата 16 с, «создать потребность + подборка» 12 с, категории с рынком 9,6 с, приглашения работодателя 7,5 с, отчёт `/validation` 4,1 с (p95 21 с) |
| api (2 воркера) | CPU макс. 254 %, в среднем 193 % (единицы одного ядра; потолок двух воркеров — 200 %); память макс. 1412 МиБ, `memory.peak` 1471 из 1536 МиБ, `oom_kill` 0 |
| db / keycloak | db CPU макс. 102 %, в среднем 47 %, 197 МиБ; keycloak 309 МиБ |
| Сервер | load average макс. 11,3 на 4 ядрах |
| Всплеск 5 холодных входов | вход 3,8–9,0 с, первый экран ≤ 10,5 с, 0 ошибок (запас 5 песочниц) |
| Журнал nginx (окно прогона) | 8261 строка: 200 — 8120, 201 — 55, 302 — 37, 429 — 5, 500 — 35, 504 — 8; Locust — 8217 запросов (−44: 37 из них — переходы 302 по личной ссылке, Locust считает их одним запросом) |

**Причина 500** — журнал api: 36 × `QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30`.
На воркер — до 40 потоков FastAPI и 15 соединений с БД; тяжёлые запросы (отчёт `/validation` — до 2000 сессий из
БД и 105 КБ JSON на каждый запрос, подборка, «Красная кнопка») держали соединение всё время расчёта, остальные ждали
30 с и падали 500 — на любых экранах (`/api/candidate/invitations`, `/assessment/status`, `/employer/needs` …).
504 отчёта — nginx не дождался ответа за 60 с. Оба воркера при этом упирались в CPU (193 % из 200 %): Python
исполняет один поток воркера за раз, поэтому очередь растёт быстрее, чем освобождаются соединения.

Сеть: генератор — песочница рабочего места за рубежом. 10.10 выяснилось, что часть соединений зарубежных площадок
с сервером обрывается примерно на 16 КБ (сеть, не продукт). В этом прогоне обрывов не зафиксировано (код 0 — ни
одного, до nginx дошло не меньше, чем отправил Locust), но **клиентские задержки включают этот маршрут и могут быть
завышены**; серверные числа (коды nginx, журнал api, `docker stats`) от сети не зависят. Повторный прогон — через
прокси ближе к серверу (с пометкой маршрута) или генератором на самом сервере.

### 6.2. Что исправлено

| Было | Стало | Где |
|---|---|---|
| Пул 5 + 10 на воркер, ожидание 30 с, затем 500 | `DB_POOL_SIZE` 8, `DB_MAX_OVERFLOW` 10, `DB_POOL_TIMEOUT_S` 10; не дождались — **503 `db_busy` с `Retry-After: 3`** и понятным текстом; в журнале api — предупреждение с методом и путём запроса | `core/config.py`, `core/db.py`, `main.py` |
| Отчёт `/validation` считается на каждый запрос и держит соединение | готовый ответ на воркер `VALIDATION_REPORT_TTL_S` = 20 с: считает один поток, остальные получают прошлый ответ (пока идёт пересчёт — тоже прошлый); соединение возвращается в пул до сериализации JSON | `validation/router.py` |
| Вызов модели и расчёты без БД держат соединение | `db.release()` перед долгой работой без БД: резюме (разбор файла, NER, модель), синхронный и фоновый разбор потребности, создание потребности без готовых требований, симуляция утечки банка | `profiles/candidate_router.py`, `matching/*`, `validation/router.py` |
| Фронтенд повторял GET после 5xx мгновенно | повтор через `Retry-After` (иначе 1 с, 2 с; не дольше 5 с) | `frontend/src/lib/api.ts` |
| Исключение при отрисовке — белый экран | граница ошибок: «Не удалось показать страницу» с кнопкой «Обновить»; переход по меню снимает ошибку | `frontend/src/components/ErrorBoundary.tsx` |

Порядок ожиданий: соединение с БД — 10 с, запрос фронтенда — 15 с (затем повтор), nginx — 60 с: пользователь
получает понятный отказ раньше, чем фронтенд оборвёт запрос.

Не изменено намеренно: оценка открытого ответа моделью держит соединение и блокировку строки сессии теста на время
вызова модели — блокировка не даёт двум параллельным запросам выдать два задания; таких запросов одновременно не
больше, чем кандидатов, отвечающих на открытые задания полного теста.

### 6.3. До/после — локальный замер

`tools/loadtest/bench_pool.py`: 40 потоков по кругу запрашивают отчёт `/validation`, статус теста и приглашения
кандидата, 90 с. Локальный стенд: SQLite, **1 воркер**, 2 общих ядра рабочего места (load average 9–16 от соседних
процессов) — абсолютные секунды со стендом не сравнимы, сравниваются три прогона подряд в одних условиях. Данные —
`docs/loadtest/local_pool_{before,after_nocache,after}.json`.

| Версия | Запросов/с | Ошибки | Отчёт p50 / p95 | Статус теста p50 / p95 | Приглашения p50 / p95 |
|---|---:|---|---|---|---|
| До (пул 5 + 10, 30 с, отчёт на каждый запрос) | 1,3 | 7 × 500 (`QueuePool … timeout 30`) | 35,2 / 48,1 с | 26,4 / 36,9 с | 22,5 / 30,1 с |
| Только пул и 503 (`VALIDATION_REPORT_TTL_S=0`) | 2,8 | 72 × 503 `db_busy`, `Retry-After: 3`; 500 нет | 18,7 / 35,2 с | 9,1 / 17,9 с | 9,6 / 17,5 с |
| После (пул, 503, кэш отчёта 20 с) | **24,1** | **0** | **0,14 / 0,9 с** | 2,9 / 4,5 с | 1,6 / 3,0 с |

Вывод: пул и 503 сами по себе нагрузку не снимают — отказы становятся быстрыми и понятными (503 за ≤ 10 с вместо
500 через 30 с), фронтенд повторяет запрос через 3 с. Пропускную способность дал кэш отчёта: самый тяжёлый запрос
перестал занимать CPU и соединения при каждом обращении.

### 6.4. Стенд после исправления

Повтор 100 и 200 пользователей — после выкладки исправления и по согласованию с администратором стенда, в окно без
проверок; числа — сюда. Ожидаемое: 500 из-за пула нет (в худшем случае — 503 с `Retry-After`), отчёт `/validation` —
из кэша; предел двух воркеров по CPU остаётся (раздел 8).

### 6.5. Как читать сводку

Сводка `run_load.py summary`:

- **Время** — с машины генератора (Москва ↔ песочница рабочего места), то есть с сетью; p50/p95/p99 — по операциям,
  строка «Всего» — по всем запросам. Строка «потребность: модель уточнила разбор (фон)» — не ответ API, а время до
  готовности фонового разбора моделью (опрос раз в 1,5 с, до 60 с).
- **Ошибки** — ответы, которые сценарий считает сбоем. Правила продукта сбоем не считаются: 409
  `invitation_cooldown` (повторное приглашение), 429 «Красной кнопки» (12 атак в минуту на учётку), 429 стартов теста
  (30 в сутки на демо-учётку), 409 закрытой сессии теста. **«429 лимит nginx для одного адреса (страницы)»** — защита
  nginx хоста от одного адреса (генератор — один адрес), а не отказ приложения; у экспертов с разных адресов её нет.
- **Код 0, обрыв связи, тайм-аут** — ответа нет. Сверка `run_load.py nginx`: если до nginx дошло меньше запросов,
  чем отправил Locust (разница > 0 при кодах 0), часть запросов потерялась по дороге от генератора; если дошли и
  получили 5xx — это ответ стенда, разбирать по журналу api.
- **Ресурсы** — `docker stats` в процентах одного ядра (4 ядра = 400 %), память контейнеров; `memory.peak` api — с
  запуска контейнера, `oom_kill` до и после прогона: рост — OOM воркера во время прогона.
- **Песочницы**: прогон создаёт до 11 новых (одна на прогон и по 5 на всплеск в каждом из двух прогонов), хранится
  не больше 60 (самые давние вытесняются). 10.10 утром на стенде было 2 песочницы — вытеснения песочниц экспертов
  нет; `cleanup` удаляет песочницы прогона.

## 7. Развёртывание с нуля по README

**Проверяющему**: развёртывание с нуля — на отдельной машине; если на той же, где уже работает копия, — сначала
`export COMPOSE_PROJECT_NAME=… WEB_PORT=… API_PORT=…` (README, «Проверено с нуля» — вторая копия), иначе команды сработают по
работающей копии.

Где: временная копия на сервере стенда (на поде проверок Docker нет) — каталог `/opt/spectrek_fsp/scratch_<время>`,
compose-проект `fspscratch`, порты только `127.0.0.1:8190` (сайт) и `127.0.0.1:5190` (API), лимиты CPU через
файл-дополнение, перед стартом — проверка ≥ 6 ГБ свободно (было 19 ГБ). Контейнеры стенда не затрагивались. После
проверки удалено всё: контейнеры, том `fspscratch_db_data`, сеть, образы `fspscratch-api`/`fspscratch-web`, каталог.
Кэш сборки Docker общий со стендом — его не чистили (≈ 1 ГБ от сборки без кэша).

Порядок (журнал без секретов — [docs/loadtest/fresh_deploy_0910.txt](loadtest/fresh_deploy_0910.txt)):

| Шаг | Время |
|---|---|
| `git clone` из бандла ветки (нет `.env`, `node_modules`, кэшей) + `make env` | 1 с |

`tools/ci/fresh_check.py` (только стандартная библиотека): `/api/health`, страницы `/`, `/validation`, `/criteria`,

удаление песочницы проверки. После запуска: api 394 МиБ из 1536, db 85 МиБ, web 5 МиБ.

Отклонения от README и исправления (README, раздел «Развёртывание на сервере» → «Проверено с нуля»):

1. **На сервере нет `make`** (Ubuntu Server ставится без него), а README начинается с `make env && make up` — в
   README добавлены те же команды без `make` (`.env` со случайными секретами, `docker compose up -d --build`, демо-данные).
2. **Вторая копия на том же сервере** заменила бы контейнеры первой: в `docker-compose.yml` задано имя проекта
   `spectrek_fsp`, а `docker compose exec … demo.seed --reset` и `make down` без своего имени сработали бы по
   основной копии. В README — `export COMPOSE_PROJECT_NAME=… WEB_PORT=… API_PORT=…` до первой команды (проверено:
   переменная важнее имени из файла).
3. **Первый вход жюри сразу после запуска или после демо-данных — 19–32 с** (запасной песочницы ещё нет: загрузка
   демо-данных удаляет песочницы, созданные до неё) — в README предупреждение; на стенде запас готовится заранее.

## 8. Узкие места и что смотреть

- **CPU двух воркеров** — главный предел стенда (10.10: 193 % из 200 % при 100 пользователях). Воркер Python
  исполняет один поток за раз, поэтому потоков FastAPI больше ядер не прибавляют. Сервер — 4 ядра: третий воркер
  (`API_WORKERS=3`) даст до 300 %, но потребует памяти (`API_MEM_LIMIT`, ≈ 700 МиБ на воркер под нагрузкой;
  10.10 — 1471 МиБ на два) и пересчёта пула. Решение — за администратором стенда, после замера.
- **Пул соединений с БД**: `API_WORKERS × (DB_POOL_SIZE + DB_MAX_OVERFLOW) ≤ PG_MAX_CONNECTIONS − 14`
  (Keycloak — `KC_DB_POOL_MAX_SIZE` 6, резерв суперпользователя PostgreSQL — 3, миграции, резервная копия и консоль —
  ≈ 5). По умолчанию 2 × (8 + 10) = 36 ≤ 50 − 14. Для трёх воркеров: `DB_POOL_SIZE=6`, `DB_MAX_OVERFLOW=6`
  (3 × 12 = 36) или `PG_MAX_CONNECTIONS=80` при памяти db не меньше 512 МиБ. Переменные — `.env.example`.
- **Следующие кандидаты на ускорение** (по p50 прогона 6.1): вакансии кандидата (индекс доверия считается на каждую
  вакансию списка), «категории с рынком» и приглашения работодателя, создание потребности с первой подборкой.

- **Создание песочницы при входе** — главное узкое место дня оценки (раздел 5): по очереди, секунды CPU, блокирует
  воркер. Дёшево снимается запасом песочниц (`JURY_SPARE_SANDBOXES`).
- **Тяжёлые первые запросы** после старта или сброса кэша: отчёт `/validation` (локально p50 0,9 с, p95 3,2 с),
  «категории с рынком» у работодателя (4,5 с), карточка кандидата и старт теста под всплеском (5–9 с) — считаются
  один раз и кэшируются; на стенде смотреть p95 после разгона.
- **«Красная кнопка» вне кэша** — симуляция утечки банка `leak_bank` локально под всплеском дала выброс 56 с при
  медиане 0,25 с; на стенде проверить отдельно (строка «/validation: красная кнопка (leak_bank)»).
- **Память api**: создание песочницы, разбор PDF и симуляции «Красной кнопки» дают всплески (07.10 при лимите 640 МиБ
  был OOM воркера — [LOAD_TEST.md](LOAD_TEST.md)); сейчас лимит 1536 МиБ, прогон записывает `memory.peak` и `oom_kill`.
- **Один адрес генератора** упирается в `limit_req` nginx для страниц — это защита, а не предел приложения; API этим
  лимитом не ограничен.
