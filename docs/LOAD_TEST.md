# Нагрузочный тест: 50 одновременных пользователей

Дата: 05.10.2026, 13:56–14:00 UTC. Стенд: прод https://fsp.neuropeople.pro (сервер «Москва», 4 vCPU, 7,9 ГБ ОЗУ,
общий с другими проектами). Версия: main `d65ba16`. Режим — «спокойный»: паузы 1–3 с между действиями,
как у живого пользователя; это проверка запаса, а не стресс-тест до отказа.

## Сценарий

Инструмент — Locust 2.46 (`tools/loadtest/locustfile.py`), запуск с внешней машины:

```bash
locust -f tools/loadtest/locustfile.py --host https://fsp.neuropeople.pro --headless -u 50 -r 5 -t 4m --csv docs/loadtest/run
```

| Пользователи | Операции (вес) |
|---|---|
| 30 работодателей (демо-компании) | версия подборки потребности (3), карточка кандидата (3), поиск по базе с фильтрами (3), категории с рынком (1) |
| 20 кандидатов (временные учётки) | начать тест (адаптивный движок банка), получить задание (2), ответить (3), статус категории (1) |

- 50 пользователей набраны за 10 с (5 в секунду), затем 4 минуты постоянной нагрузки.
- Кандидаты — временные учётки `loadtest-*@demo.invalid` (скрыты от работодателей), созданы
  `tools/loadtest/lt_accounts.py` внутри контейнера api и **удалены после теста** (40 учёток вместе с сессиями).
- Ответы отправлялись только на задания с выбором варианта или строки; открытые ответы пропускались, чтобы не
  нагружать внешнюю LLM-оценку. Поэтому ответов мало (35): кандидат, дойдя до открытого задания, дальше только
  запрашивает его.

**Находка 07.10: OOM api при 640 МиБ.** В 13:18 МСК воркер uvicorn убит ядром по лимиту памяти: `memory.peak`

песочницы и разбора текста потребности через LLM; uvicorn поднял новый воркер за 5 с, контейнер не
перезапускался, но запрос, который обрабатывал воркер, оборвался. Обычное потребление api — 457–508 МиБ (2 воркера
по 250–320 МиБ: NER Natasha, банк заданий, модели подбора, кэши), сверху — всплески: создание песочницы, разбор PDF
в отдельном процессе (предел 256 МиБ), симуляция «Красной кнопки» вне кэша (~140 МиБ). Нагрузочный тест 05.10
такие всплески не ловит (297 МиБ): в сценарии нет разовых тяжёлых действий. Лимит api — 768 МиБ (508 + ~260 МиБ
на всплеск); весь стек — 1 696 МиБ, без профиля `fsp-id` — 1 120 МиБ. Мониторинг стенда пишет о памяти api ≥ 90 %
и о каждом новом OOM (docs/ARCHITECTURE.md, раздел 11.1).

Load average сервера — не выше 1,39 (4 ядра).

## Выводы

- 50 одновременных пользователей прототип держит без ошибок; 95 % ответов — до 0,3 с с учётом сети.
- Запас: api загружен в среднем на 28 % одного ядра, память всего стека — 0,64 ГБ при бюджете 1,5–2 ГБ.
- Самая тяжёлая из частых операций — поиск по базе с фильтрами (95 % — 420 мс): ранжирование и объяснения считаются в приложении по всей
  базе. При росте базы — предварительный отбор в SQL и кэш категорий.
- Узкое место при росте — один процесс api на 2 воркерах; масштабирование — число воркеров uvicorn и
  отдельный пул соединений PostgreSQL.

## Прогон против стенда (после выкладки)

Команды — `tools/loadtest/run_stand.sh`. Учётки создаются и удаляются на сервере, Locust запускается с другой
машины (иначе CPU теста смешается с сервером); сайт закрыт паролем, но API открыт — Locust ходит только в `/api/`.

```bash
# машина теста, один раз: Locust в отдельном окружении (на Python 3.14 gevent не собирается — нужен 3.12)
python3.12 -m venv /tmp/lt && /tmp/lt/bin/pip install locust==2.46.0

# сервер, из /opt/spectrek_fsp/app: временные учётки → /tmp/lt_tokens.json (JWT без паролей)
tools/loadtest/run_stand.sh setup 40
# скопировать /tmp/lt_tokens.json на машину теста (scp), там же — каталог репозитория

# сервер, параллельно с run: docker stats каждые ~8 с → /tmp/lt_docker_stats.txt
tools/loadtest/run_stand.sh stats 300
# машина теста: 50 пользователей, 4 минуты → docs/loadtest/run_*.csv
tools/loadtest/run_stand.sh run 50 4m https://fsp.neuropeople.pro

# сервер: удалить временные учётки и файл токенов (на машине теста удалить копию)
tools/loadtest/run_stand.sh cleanup
cat /sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' spectrek_fsp-api-1).scope/memory.peak
```

Что смотреть: ошибок 0; 95 % по операциям — как 05.10 (до 0,3–0,4 с с сетью); новые операции (кабинет ФСП,
отчёт валидации) — до 1 с после первого запроса; память api — ниже 768 МиБ с запасом, новых OOM в
`memory.events` нет. Результаты — в этот документ отдельным разделом с датой и версией.
