# Нагрузочный тест: 50 одновременных пользователей

Дата: 05.10.2026, 13:56–14:00 UTC. Стенд: прод https://fsp.neuropeople.pro (сервер «Москва», 4 vCPU, 7,9 ГБ ОЗУ,
общий с другими проектами). Версия: main `d65ba16`. Режим — «спокойный»: паузы 1–3 с между действиями,
как у живого пользователя; это проверка запаса, а не стресс-тест до отказа.

## Сценарий

Инструмент — Locust 2.46 (`tools/loadtest/locustfile.py`), запуск с внешней машины:

```bash
locust -f tools/loadtest/locustfile.py --host https://fsp.neuropeople.pro --headless -u 50 -r 5 -t 4m --csv docs/loadtest/run
```

| Пользователи | Операции (вес) |
|---|---|
| 30 работодателей (демо-компании) | версия подборки потребности (3), карточка кандидата (3), поиск по базе с фильтрами (3), категории с рынком (1) |
| 20 кандидатов (временные учётки) | начать тест (адаптивный движок банка), получить задание (2), ответить (3), статус категории (1) |

- 50 пользователей набраны за 10 с (5 в секунду), затем 4 минуты постоянной нагрузки.
- Кандидаты — временные учётки `loadtest-*@demo.invalid` (скрыты от работодателей), созданы
  `tools/loadtest/lt_accounts.py` внутри контейнера api и **удалены после теста** (40 учёток вместе с сессиями).
- Ответы отправлялись только на задания с выбором варианта или строки; открытые ответы пропускались, чтобы не
  нагружать внешнюю LLM-оценку. Поэтому ответов мало (35): кандидат, дойдя до открытого задания, дальше только
  запрашивает его.

## Выводы

- 50 одновременных пользователей прототип держит без ошибок; 95 % ответов — до 0,3 с с учётом сети.
- Запас: api загружен в среднем на 28 % одного ядра, память всего стека — 0,64 ГБ при бюджете 1,5–2 ГБ.
- Самая тяжёлая из частых операций — поиск по базе с фильтрами (95 % — 420 мс): ранжирование и объяснения считаются в приложении по всей
  базе. При росте базы — предварительный отбор в SQL и кэш категорий.
- Узкое место при росте — один процесс api на 2 воркерах; масштабирование — число воркеров uvicorn и
  отдельный пул соединений PostgreSQL.
